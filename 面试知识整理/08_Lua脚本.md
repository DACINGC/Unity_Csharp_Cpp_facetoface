# 八、Lua 脚本

## 8.1 基础

- `type()`：获取变量的类型，返回值类型是 string；判断为空时与 `"nil"` 比较（`type(x) == "nil"`）。
- `require`：加载文件并执行其中的代码；`./` 表示当前文件夹下的文件，`../` 表示上一级文件夹。

### 8.1.1 table 的底层结构

- table 是**混合结构**，由两部分组成：
  - **数组部分（Array Part）**：存储连续的数字索引键，类似传统数组；
  - **哈希部分（Hash Part）**：存储非数字键，通过哈希表实现。
- 内存分配是**动态的**；常见数据结构是 string 和 table。

## 8.2 遍历：ipairs 与 pairs

| 对比项 | ipairs | pairs |
| --- | --- | --- |
| 遍历范围 | 只遍历**数组部分**（整数键） | 遍历表中**所有键值对**（数组 + 哈希） |
| 起始/终止 | 从索引 1 开始依次递增，**遇到 nil 立即停止** | 遍历所有有效键，顺序不固定（依赖哈希实现） |
| 非数字键 | 忽略 | 包含 |
| 适用 | 数组型表 | 混合键表 |

## 8.3 元表与元方法

### 8.3.1 什么是元表/元方法

- 元表（metatable）是一个普通 Lua 表，可关联到另一个表上，通过特定键（元方法）定义表对某些操作的响应。
- 当对表执行某操作而表本身没有直接定义时，Lua 会查找其元表中的对应元方法。
- 常用元方法：算术（`__add`/`__sub`/`__mul`/`__div`/`__mod`/`__unm`/`__pow`）、比较（`__eq`/`__lt`/`__le`）、连接（`__concat`）、长度（`__len`）、索引（`__index`/`__newindex`）、调用（`__call`）。

### 8.3.2 __index、__newindex、__call、__tostring、rawset、rawget

| 元方法 | 触发时机 |
| --- | --- |
| `__index` | **查询**：获取当前表**没有的键**时，去元表的 `__index` 查找（`__index` 可以是表或函数） |
| `__newindex` | **赋值**：给当前表**没有的键**赋值时调用；若 `__newindex` 是一个表，则对该表字段赋值 |
| `__call` | 把表**当作函数调用**时调用 |
| `__tostring` | 表被当作字符串使用/输出时调用（如 `print(t)`） |
| `rawset` | **绕过元方法**直接设置表字段 |
| `rawget` | **绕过元方法**直接获取表字段 |

- 区别一句话：`__index` 用于**查询**，`__newindex` 用于**更新**。

## 8.4 面向对象

### 8.4.1 Lua 如何实现 OOP 三大特性

- **封装**：利用 table 封装数据与方法。
- **继承**：利用**元表 + __index** 模拟：
  - 设置子类的元表为父类；父类的 `__index` 指向父类自己；
  - 子类身上找不到属性/方法时，会查找元表的 `__index`（即父类中的内容），从而模拟继承。
- **多态**：子类自己实现同名方法即可（覆盖父类版本）。

### 8.4.2 Lua 实现 C# 的 new 构造

- 思路：把 `new` 传入的参数表作为本地表 o；把"类"（self）作为元表，设置元方法 `__index` 指向类自身；返回 o。调用 `new` 时实际访问的是元表（类）中的内容，从而模拟 C# 的 new + 构造函数。

## 8.5 进阶

### 8.5.1 闭包

- 当一个函数嵌套另一个函数时，内部函数可以访问外部函数的局部变量，**即使出了外部函数的作用域依然成立**（变量被捕获，生命周期延长）。
- 实现要点：Lua 里每个函数都是一个**闭包**——函数原型 + 捕获的 **upvalue**（外部局部变量）。多个闭包共享同一个 upvalue 时，改一个另一个也看得到。
- 常见用途：迭代器（§8.5.5）、模块私有状态、回调携带上下文。

### 8.5.2 协程（coroutine）★★★★ Lua 面试第一高频

**是什么**：协程是一段**可以挂起、之后从挂起点恢复**的执行流。与线程的区别是**协作式**——不抢占，只有协程自己调用 `yield` 才让出，所以**同一时刻只有一个在跑**，不需要锁。

**核心 API（5 个，必须能默写）**：

| API | 作用 |
| --- | --- |
| `coroutine.create(f)` | 创建协程，返回类型为 `"thread"` 的协程对象；**不会立即执行** |
| `coroutine.resume(co, ...)` | 启动或**恢复**协程，参数传给 `f`（首次）或 `yield` 的返回值（之后）；返回 `true, ...` |
| `coroutine.yield(...)` | **挂起**当前协程，把参数作为 `resume` 的返回值返回给调用方 |
| `coroutine.status(co)` | `"suspended"` 挂起 / `"running"` 正在跑 / `"normal"` 活着但没在跑（它 resume 了别的协程）/ `"dead"` 结束 |
| `coroutine.wrap(f)` | 同上但返回**函数**而非 `thread`：调用即 resume；**出错时直接抛异常**而不是返回 `false, err` |

**手写最小示例（能背下来最好）**：

```lua
local co = coroutine.create(function(a, b)
  print("开始", a, b)                -- 首次 resume 传入 1, 2
  local c = coroutine.yield(a + b)   -- 挂起，把 3 交回调用方
  print("恢复，收到", c)              -- 第二次 resume 传入 10
  return "结束"
end)

print(coroutine.resume(co, 1, 2))  -- true  3
print(coroutine.resume(co, 10))    -- 恢复，收到 10；true  结束
print(coroutine.resume(co))        -- false  cannot resume dead coroutine
print(coroutine.status(co))        -- dead
```

**关键机制要讲清的两点**：

1. **数据双向传递**：`resume` 的参数 → 成为 `yield` 的**返回值**；`yield` 的参数 → 成为 `resume` 的**返回值**。这是"用协程做生产者-消费者"的基础（消费者 resume、生产者 yield 出数据）。
2. **`create` 与 `wrap` 的错误处理差异**：`create` + `resume` 把错误当**返回值**（`false, err`），适合需要捕获的场景；`wrap` 直接在**调用点抛异常**，写法更简洁但要么外层 `pcall` 要么崩溃。**这是常见追问点**。

**与 Unity 协程的区别（项目联动，必答）**：

| | Lua 协程 | Unity 协程（`IEnumerator` + `StartCoroutine`） |
| --- | --- | --- |
| 归属 | Lua 虚拟机内部，纯用户态 | Unity 引擎调度，挂在 MonoBehaviour 上 |
| 挂起方式 | `coroutine.yield(...)`，恢复时机**由调用方决定** | `yield return xxx`，恢复时机由**引擎按指令类型**决定（帧末/物理步/秒数） |
| 与帧的关系 | **与帧无关**，可以在同一帧内 resume/yield 任意次 | **与帧绑定**，只在主线程、由引擎驱动 |
| 生命周期 | 由持有者管理（自己 resume） | 随 GameObject 销毁 / `SetActive(false)` / `StopCoroutine` 而**被强制终止** |
| 能否被外部强杀 | **不能**（只能不再 resume，等 GC） | 能（`StopAllCoroutines`） |

> 记忆：**Lua 协程是"可挂起的函数"，Unity 协程是"分帧执行的任务"**。前者是语言机制，后者是引擎调度机制——这也是为什么 Lua 协程能在一帧内切换多次，而 Unity 协程天然分帧。
> 项目里的 `UniTask` 是第三条路：`async/await` + 玩家循环（PlayerLoop），比 Unity 协程更省 GC（不必 `new WaitForSeconds`），且支持返回值与取消（`CancellationToken`）。

**实现原理（加分项）**：Lua 协程靠**独立的栈**实现——每个协程有自己的调用栈，`yield` 时保存当前栈状态并切回调用者栈，`resume` 时恢复。因为**不需要线程切换、不进内核**，开销远小于线程，但仍比普通函数调用贵（要保存/恢复栈）。这解释了为什么"协程很轻"但"每帧创建上万协程照样会卡"。

**典型用途**：状态机（把"等待某条件"写成顺序代码）、迭代器（用 `coroutine.wrap` 写生成器）、异步流程串联（先发请求、挂起等回包、再继续）、行为脚本分步执行。

### 8.5.3 深拷贝与浅拷贝

- 先区分三件事（面试常混）：
  - **赋值**（`b = a`）：只是让 `b` 指向**同一张表**，没有任何复制。改 `a.x` 或 `b.x` 都是改同一份数据。
  - **浅拷贝**：**新建一张表**，把原表的**顶层键值**复制过去。顶层增删改互不影响；但**值仍是引用**——若某个值是嵌套表，两边仍共享它，改嵌套内容两边都变。
  - **深拷贝**：递归复制所有层级（含嵌套表），两份数据完全独立。
- 手写浅拷贝（表结构由"数组部分 + 哈希部分"组成，要分别遍历）：

```lua
local function shallowCopy(t)
  local r = {}
  for k, v in pairs(t) do r[k] = v end   -- 顶层键值复制（v 若是表仍是共享引用）
  return r
end
-- 更完整的写法用 table.unpack（5.2+）/ unpack（5.1）展开数组部分，并视需要带上元表
```

- 手写深拷贝（**必须防循环引用**）：

```lua
local function deepCopy(t, seen)
  if type(t) ~= "table" then return t end
  seen = seen or {}
  if seen[t] then return seen[t] end        -- 关键：循环引用直接复用已拷贝对象
  local r = {}
  seen[t] = r
  for k, v in pairs(t) do r[deepCopy(k, seen)] = deepCopy(v, seen) end
  return setmetatable(r, getmetatable(t))   -- 视需要保留元表
end
```

- 注意：`pairs` **不保证顺序**；只复制数组部分可用 `ipairs`（但遇到 `nil` 会提前停止）。

### 8.5.4 userdata

- userdata：**用户自定义数据类型**。
- 当 C、C++、C# 与 Lua 产生交互时传入/传出的数据统称为 userdata，主要用来存储与外界交互产生的数据类型。

### 8.5.5 实现 table 的迭代器

- 直接使用 `pairs` 或 `ipairs` 实现；也可以自定义迭代器函数（闭包 + 状态变量）实现特定遍历逻辑。

## 8.6 Lua 与 C / C# 交互

### 8.6.1 Lua 与 C 交互原理

- 通过**栈**交互（类似 C 函数调用栈）：
  - C 调用 Lua：Lua 把值**压入栈**，C 再从栈中取值；
  - Lua 调用 C：C 将数据压入栈，Lua 从栈中取值。
- 正数索引表示从**栈底**开始到栈顶；负数索引表示从**栈顶**开始到栈底。

### 8.6.2 C# 与 Lua 交互原理

- 同样通过**虚拟栈**实现：
  - **C# Call Lua**：C# 把数据放入栈 → Lua 从栈取数据 → 结果返回栈顶 → C# 从栈顶取出；通过**桥文件访问 dll** 实现访问。
  - **Lua Call C#**：C# 源文件生成 **Wrap 文件**或生成 C 模块，注册到 Lua 解析器，Lua 调用该模块的函数（如 xLua/ToLua 框架原理）。

## 8.7 内存、GC 与热更新

### 8.7.1 Lua 的 GC 原理（三色标记）

- 标记阶段：遍历所有**可达**对象，标记为活跃。
- 清理阶段：遍历待析构/未标记对象，把其中仍被引用的对象标记为活跃。
- 清除阶段：回收所有未被标记为活跃的对象。
- 析构阶段：调用清理阶段分离出的对象的析构器。
- 每个对象有三种状态：
  - **白色**：**尚未被标记**（所有对象在标记开始前都是白色）。标记结束后**仍是白色**的才是垃圾，被清除阶段回收；
  - **灰色**：**已被发现但子对象还没扫描完**（在灰色链表里等待处理，是"待展开的边界"）；
  - **黑色**：**自身与所有子对象都已扫描完**（确定存活）。
- **为什么必须三色 + 增量**：Lua 的 GC 是**增量式**的（按步长分多次执行），标记过程会被打断，期间程序还在改引用关系。
- **三色不变式**：不允许出现"**黑色对象直接指向白色对象**"。若被打破，那个白色对象可能被漏标而误回收。维护不变式的机制就是**写屏障（write barrier，Lua 里是 `luaC_barrier` 系列）**：当把一个白色对象写进黑色对象的字段时，屏障会把它重新拉回灰色（或把黑色对象退回灰色），保证不漏标。
- **这就是面试追问的落点**："增量标记怎么保证不误回收？" → 答**三色不变式 + 写屏障**，而不是背"白灰黑"三个字。
- 补充：Lua 5.4 引入**分代模式**（`collectgarbage("generational")`），区分新旧两代，多数回收只处理新对象以降低长停顿；跨代引用同样靠写屏障维护。

### 8.7.2 Lua 如何实现热更新

**先分清两件事**（原答案答的是"资源热更"，不是"代码热更"，这是本题最容易答偏的地方）：

| | 资源热更 | **Lua 代码热更** |
| --- | --- | --- |
| 更新对象 | AB 包 / 图集 / 配置 / 音频等**资产** | `.lua` **脚本逻辑** |
| 机制 | 清单比对 → 差异下载 → 替换本地包 | 重写 loader → 重新 `require` → 处理旧引用 |
| 能否改逻辑 | 不能 | **能**（这正是"为什么用 Lua"的全部理由） |

**资源热更（Lua 逻辑也常以文本/字节形式随包下发）**：
1. 从服务器下载**资源清单/比对文件**（含每个资源的 Hash 与版本）；
2. 与**本地清单**比对，算出新增/变更/删除的差异项；
3. 按差异下载新包，替换本地旧包并更新本地清单；Lua 脚本文件本身也走这套流程。

**Lua 代码热更的核心机制**（面试真正想听的）：

1. **自定义 loader**：`require` 内部走 `package.loaders`/`package.searchers` 链。框架（xLua/ToLua/tolua）往里插入自己的 searcher，从**自定义路径**（可写目录 / AB 内的 Lua 文件）而不是只从 `package.path` 找模块。这是"能加载到新代码"的前提。
2. **清缓存 + 重新 require**：`require` 会把结果缓存进 `package.loaded[模块名]`，**第二次 require 直接返回缓存**。所以热更必须：
   ```lua
   package.loaded["game.battle.skill"] = nil      -- 清掉旧模块
   local newSkill = require("game.battle.skill")  -- 重新加载，得到新实现
   ```
   批量热更需要按**依赖顺序**处理（先热更被依赖的底层模块）。
3. **旧引用是最大难点**（面试追问点）：已经持有旧函数的对象不会自动切换——
   - 其它模块在热更前就 `local f = oldModule.func` 拿到的 **upvalue 仍指向旧函数**；
   - 已经注册到事件总线/UI 回调的**旧闭包**、正在运行的**协程**（持有旧栈）都还跑旧逻辑。
   - 常见处理：热更后**重新注册**回调；协程等它自然结束或显式重启；对"必须立刻生效"的入口改为**每次调用都查表**（`M.func()` 而非 `local func = M.func`）——这也是 Lua 侧性能与热更之间的权衡。
4. **对已实例化对象的影响**：数据（table 字段）不会自动迁移。若新版给表加了字段，旧实例缺字段 → 需要**版本号 + 迁移函数**，或让对象在下次创建时自然采用新结构。
5. **xLua 的 hotfix 是另一条路**：不重载整个模块，而是用 **IL 注入**给已编译的 C# 方法打桩——运行时先查"这个方法有没有 Lua 补丁"，有就跳去执行 Lua 函数。适合**只改几个 C# 方法**、不想重载模块的场景；Lua 纯逻辑热更仍走上面的 loader 方案。

**答题收尾**：Lua 热更的价值不是"能下载新文件"，而是"**能在不重启进程的前提下替换逻辑**"；真正的工作量在**引用失效与状态迁移**，而不在下载。

### 8.7.3 AB 包资源加载的方法（Lua 侧涉及）

1. 从本地文件加载（`AssetBundle.LoadFromFile`）；
2. 从本地内存加载（`AssetBundle.LoadFromMemory`，官方不推荐：内存双份、不支持压缩包）；
3. `UnityWebRequestAssetBundle` 网络加载（旧版为 `WWW`，已过时；`WWW.LoadFromCacheOrDownload(url, version)` 带版本号做本地缓存）；
4. 通过 Manifest 文件加载（`LoadFromFile` 拿 Manifest，读依赖关系）；
5. 从 Stream 流式加载（`LoadFromStream`，用于加密或自定义压缩场景）。
