# 二、C++ 语言

## 2.1 内存管理

### 2.1.1 C++ 程序内存分区

| 区域 | 存储内容 | 管理方式 |
| --- | --- | --- |
| 栈区 | 函数调用时的局部变量、函数参数、返回地址 | 编译器自动分配/释放 |
| 堆区 | 动态分配的内存（new / malloc） | 需手动释放 |
| 全局/静态区 | 全局变量、静态变量（分已初始化区、未初始化区） | 程序生命周期内存在 |
| 代码区 | 程序二进制代码（函数体、类方法） | 只读 |

### 2.1.2 内存泄漏与内存碎片

| 问题 | 原因 | 避免方法 |
| --- | --- | --- |
| 内存泄漏 | 未释放内存、指针丢失、异常未处理 | 智能指针、RAII（资源获取即初始化）、异常安全代码 |
| 内存碎片 | 频繁分配/释放、大小不一 | 内存池、对象池、减少动态内存分配 |

### 2.1.3 new 与 malloc 的区别

| 对比项 | new | malloc |
| --- | --- | --- |
| 类型安全 | 自动计算所需内存大小，返回类型化指针 | 手动计算大小，返回 `void*`，需显式转换 |
| 初始化 | 自动调用构造函数 | 仅分配内存，不初始化 |
| 释放 | `delete`，自动调用析构函数 | `free`，不调用析构函数 |
| 失败处理 | 抛出 `std::bad_alloc` 异常 | 返回 NULL |
| 功能扩展 | 支持运算符重载 | 不支持 |
| 适用场景 | C++ 中动态创建对象 | C 风格内存分配或与 C 库兼容场景 |

### 2.1.4 delete 与 delete[] 的区别

- `delete` 释放单个对象，调用该对象的析构函数。
- `delete[]` 释放对象数组，逐个调用每个元素的析构函数。
- 错误混用（new[] 配 delete 或 new 配 delete[]）会导致**未定义行为**（可能内存泄漏或崩溃）。

### 2.1.5 智能指针与 RAII

- **RAII**：资源获取即初始化——用对象生命周期管理资源（内存、文件句柄、锁），析构时自动释放。
- `unique_ptr`：独占所有权，不可拷贝。
- `shared_ptr`：共享所有权，引用计数归零时释放。
- `weak_ptr`：弱引用，不增加引用计数，用于打破循环引用。
- 裸指针 `new`/`delete` 在现代 C++ 中应尽量用智能指针替代。
- 智能指针的线程安全边界与循环引用详见 §2.6.7。

### 2.1.6 内存对齐、结构体大小与位域（★★★ 高频）

- **为什么要对齐**：CPU 按字长成批读内存，**未对齐的访问可能跨越两个内存字**，要多次访存甚至触发异常（部分架构直接崩）。对齐后一次读出。
- **三条规则（算结构体大小的口诀）**：
  1. 每个成员的**偏移量**必须是 `min(成员自身大小, 编译器对齐系数)` 的整数倍，不足则填充（padding）；
  2. 结构体**总大小**必须是**最大成员对齐值**的整数倍，末尾补齐（trailing padding）；
  3. **嵌套结构体**按其"最大成员对齐值"参与外层计算（不是按它补齐后的总大小）。
- **手算示例**：

```cpp
struct A { char a; int b; char c; };        // 1 + pad3 + 4 + 1 + pad3 = 12
struct B { int b; char a; char c; };        // 4 + 1 + 1 + pad2       = 8
struct C { char a; double d; char c; };     // 8 字节对齐：1+pad7 + 8 + 1+pad7 = 24
struct D { char a; struct { int x; } s; };  // 内层对齐 4：1+pad3 + 4 = 8
```

- **结论**：成员**按大小从大到小排列**能减少填充（A=12 → B=8）。这不是微观优化——在 ECS/SoA 布局里它直接决定缓存行利用率（§4.3.4、§10.16）。
- **手动控制对齐**：
  - **取消填充**：`#pragma pack(1)` 或 `__attribute__((packed))`（GCC）/ `#include <cstddef>` + `alignas`；**代价是未对齐访问变慢**，多用于**网络协议/文件格式**（必须与对方字节布局完全一致）。
  - **强制对齐**：`alignas(64)` 让对象对齐到缓存行，用于避免**伪共享**（§4.3.4）。
  - 查询：`alignof(T)` 取对齐值，`offsetof(T, member)` 取成员偏移（需 `<cstddef>`）。
- **`sizeof` 的空类与虚函数**：空类 `sizeof == 1`（保证每个对象有唯一地址）；含虚函数的类要多一个 **vptr**（64 位平台通常 8 字节）。
- **位域（bit-field）**：`struct { unsigned a : 3; unsigned b : 5; }` 按**位**分配，用于紧凑存储标志位。
  - **陷阱**：位域的**内存布局是实现定义的**（跨编译器/平台可能不同），**不能**用于网络协议或跨进程共享内存；且位域**不能取地址**（`&s.a` 非法）。
  - 想要可移植的位操作，用显式掩码（§2.7.3 的"某位清 0 / 置 1"）而不是位域。
- **与 Unity/C# 的对应**：C# 侧用 `[StructLayout(LayoutKind.Sequential, Pack = 1)]` 控制布局以对接 C/C++ 或网络协议；`Marshal.SizeOf` 与 `sizeof` 在含引用字段时结果不同（§4.3.3）。

## 2.2 指针与引用

### 2.2.1 引用与指针的区别

| 对比项 | 引用 | 指针 |
| --- | --- | --- |
| 定义 | 变量的别名，必须初始化 | 存储地址的变量，可稍后赋值 |
| 重新绑定 | 不能重新指向其他对象 | 可以改变指向 |
| 空值 | 不能为 null（必须绑定对象） | 可以为 nullptr |
| 运算 | 无指针运算（++、-- 等） | 支持算术运算 |
| 内存 | **语言层面不保证额外存储**；实现上通常就是常量指针，会占一个指针大小（优化后可能被完全消除） | 占用一个指针大小的内存 |
| 安全 | 相对安全 | 易产生野指针、越界 |

### 2.2.2 指针常量与常量指针

- **常量指针（pointer to const）**：`const int *p` / `int const *p`——指向常量的指针，**不能通过 p 修改指向的值**，但 p 可以指向别处。
- **指针常量（const pointer）**：`int *const p`——指针本身是常量，**p 不能再指向别处**，但可以通过 p 修改指向的值。
- 记忆：`const` 修饰谁，谁不可变。`const char *p` 与 `char *const p` 同理。

### 2.2.3 野指针的成因与避免

- **成因**：
  1. 未初始化的指针（指向随机地址）；
  2. 指向已释放的内存（free/delete 后未置空）；
  3. 指针越界（超出数组或动态分配内存范围）；
  4. 返回局部变量的地址（局部变量销毁后指针失效）。
- **避免**：声明时初始化（或置 `nullptr`）、释放后置空、不返回局部对象地址、用智能指针。

### 2.2.4 数组名与指针、a 与 &a 的区别

- 数组名是**首元素地址的常量**（不是变量，不能自增/被赋值），`sizeof(数组名)` 得到整个数组大小。
- 指针是变量，`sizeof(指针)` 得到指针本身大小（如 8 字节 64 位）。
- `int a[5]`：`a` 是首元素地址（`int*`）；`&a` 是整个数组的地址（`int(*)[5]`），两者数值相同但类型不同，`a+1` 跳过一个元素，`&a+1` 跳过整个数组。
- 数组作为函数实参时会**退化为指针**（丢失长度信息）。

### 2.2.5 函数指针与指针函数

- **函数指针**：指向函数的指针，`int (*fp)(int, int)`，用于回调、表驱动。
- **指针函数**：返回值为指针的函数，`int* func()`。

### 2.2.6 如何避免悬垂/越界等指针问题

- 对应经典题"如何避免野指针"：初始化、置空、智能指针、边界检查。

## 2.3 关键字

### 2.3.1 const

- 定义不可修改的常量，或限制对数据的修改权限；声明时必须初始化，类型安全。
- `const` 成员函数：承诺不修改对象状态（`mutable` 成员除外）。
- 常引用（`const T&`）：既能避免拷贝开销，又能保证只读，常用于函数参数。

### 2.3.2 static

| 场景 | 作用 |
| --- | --- |
| 静态局部变量（函数内） | 延长生命周期至程序结束，仅初始化一次，作用域仍限函数内 |
| 静态成员变量（类内） | 属于类本身，所有实例共享同一份数据；必须在类外单独初始化 |
| 静态成员函数（类内） | 无需实例即可调用，无 `this` 指针，只能访问静态成员 |
| 静态全局变量/函数（文件作用域） | 内部链接，仅当前文件可见，避免命名冲突 |

### 2.3.3 extern 与 extern "C"

- `extern`：声明变量/函数具有外部链接性，定义在其他文件或作用域中。
  - **带初始化的 `extern` 是"定义"而非"声明"**：`extern int x = 5;` 合法，它就是一个定义（全程序只能出现一次），此时 `extern` 只影响链接性；不加初始化的 `extern int x;` 才是纯声明。
  - 命名空间作用域的 `const` **默认内部链接**（每个 .cpp 各有一份），要让多个文件共享同一个 const 对象需写 `extern const int x = 5;`（定义处）+ `extern const int x;`（使用处）。
  - 全局变量必须且只能在一个文件中定义（ODR）。
- `extern "C"`：告诉 C++ 编译器按 **C 语言方式**处理符号（不进行名字修饰/重载），用于在 C++ 中调用 C 函数或让 C 调用 C++ 函数。

```cpp
extern "C" {
    void my_function(int a, int b);
}
```

### 2.3.4 volatile

- 告诉编译器该变量可能被**本程序之外**的因素修改（硬件寄存器、内存映射 IO、信号处理函数），**不要优化掉对它的读写**，每次直接访问内存。
- 可以修饰指针（如指向硬件寄存器的指针）。
- **`volatile` 不是线程同步工具**（这是最高频的误区）：
  - 它**不保证原子性**（`v++` 仍是读-改-写三步，可能丢失更新）；
  - 它**不建立 happens-before / 内存屏障**，不保证多核间的可见性顺序；
  - C++11 起，**跨线程共享数据应当用 `std::atomic` + 明确的内存序**（§2.6.5），或用互斥量。
  - 正确用途只剩：**内存映射 IO、硬件寄存器、`setjmp/longjmp`、信号处理里与 `sig_atomic_t` 配合**。
- 对比记忆：**`volatile` 管"别优化掉这次访问"，`atomic` 管"这次访问是原子且有序的"**。

### 2.3.5 typedef 与 #define 的区别

- `typedef`：为类型起别名，编译期处理，有类型检查。
- `#define`：文本宏替换，预处理期处理，无类型检查；定义宏时注意**整体加括号**防止优先级问题。

```cpp
#define MIN(a, b) ((a) < (b) ? (a) : (b))   // 标准 MIN 宏
```

- **`MIN` 宏最常见的追问：参数被求值两次**。`MIN(i++, j)` 里较小的那个会自增**一到两次**（因为 `a` 在宏体里出现两遍），行为未定义/结果依赖实现——这是宏最典型的陷阱。
- **同一原因的其它坑**：`MIN(f(), g())` 会多调用一次函数；`MIN(a, b) + 1` 若不加外层括号会算错（所以宏体与参数都要加括号，如上写法）。
- **正确替代**：
  - C++ 里优先用 **`std::min` / `std::max`**（模板函数，参数只求值一次，有类型检查）；
  - 必须用宏时，用 **`inline` 函数**或 `({ ... })` 语句表达式（GCC 扩展，不可移植）；
  - 需要常量表达式时用 C++14 的 `constexpr` 函数。
- 记忆：**宏是文本替换，不是函数调用**——"参数求值次数"与"括号"是宏题永恒的两个考点。

### 2.3.6 inline 与虚函数、构造函数

- 内联函数：编译期将函数体展开，减少调用开销；适合短小、频繁调用的函数。
- 虚函数可以声明为 `inline`，但**通过虚表调用时不会内联**（虚调用需要运行期动态绑定，与内联的静态展开语义冲突）。
  - **但"不会被内联"不是绝对的**：编译器在能确定动态类型时会做**去虚化（devirtualization）**——例如对象是栈上具体类型、方法被标 `final`、或开启 LTO 后能证明唯一实现——此时虚调用退化为直接调用，**可以内联**。所以准确说法是"**虚调用通常不内联；去虚化之后可以**"。
- **构造函数不能是虚函数**：虚函数依赖虚表实现多态，而虚表/虚指针的初始化发生在构造函数执行阶段；构造函数的类型必须在编译时确定。

## 2.4 面向对象

### 2.4.1 面向对象三大特性

- **封装**：将数据和方法捆绑成类，隐藏内部细节，暴露接口。
- **继承**：子类继承父类的属性和方法，通过重写/扩展实现代码复用。
- **多态**：同一操作在不同环境下产生不同行为——编译时多态（重载、模板）、运行时多态（虚函数 + 动态绑定）。

### 2.4.2 class 与 struct 的区别

- 默认访问权限不同：`class` 默认 `private`，`struct` 默认 `public`。
- C++ 中两者都可以有成员函数、继承（区别于 C 的 struct）。

### 2.4.3 空类的大小与默认成员函数

- 空类 `sizeof(A)` 为 **1**（编译器给一个占位字节，保证不同对象有唯一地址，不能为 0）。
- 编译器自动生成的默认函数——**C++11 起是六个**（旧标准只算四个）：
  1. 默认构造函数
  2. 析构函数
  3. 拷贝构造函数
  4. 拷贝赋值运算符
  5. **移动构造函数**（C++11）
  6. **移动赋值运算符**（C++11）
  - **关键规则**：**一旦用户声明了其中某一个，对应的隐式版本就不再生成**。典型坑：写了析构函数，编译器仍会生成拷贝构造（不推荐但会发生），却**不再生成移动构造**——于是"看起来有移动语义"的代码实际走了拷贝，性能悄悄退化。所以自定义了资源管理就要按 **Rule of Five** 把五个（析构 + 拷贝构造/赋值 + 移动构造/赋值）一起考虑（见 §2.6.1）。

### 2.4.4 拷贝构造函数与赋值运算符

- **拷贝构造**：用一个对象初始化另一个对象时调用（`A a2 = a1;`）。
- **赋值运算符**：已存在的对象之间赋值时调用（`a2 = a1;`）。
- 拷贝构造调用时机：① 用一个对象初始化另一个对象；② 值传递参数；③ 值返回对象。
- **必须重写拷贝构造的情况**：类含动态内存分配（默认浅拷贝会导致多个对象指向同一块堆内存，析构时双重释放）；持有不可拷贝资源（文件句柄、网络连接）；需要严格控制拷贝语义（单例、引用计数）。

### 2.4.5 构造函数与析构函数

- 构造函数：初始化对象；可以有参/无参；可以被重载。
- 析构函数：销毁对象、释放资源；**不能重载**（销毁语义唯一，无需参数化）。
- **析构函数应当是虚函数**——但准确的**前提是"会通过基类指针 delete 派生类对象"**，而不是"只要被继承就必须虚"：
  - 若确实会 `Base* p = new Derived; delete p;`，而基类析构非虚 → **派生类析构不会被调用**，资源泄漏（UB）；
  - 若基类**从不**被用于多态删除（如纯接口以外的工具类、或只作栈上使用），加虚析构反而**白白引入 vptr**（增大对象、影响 POD 与内存布局、阻碍某些优化）；
  - **经验规则**：**类里只要有一个虚函数，就应该有虚析构**；否则要保证不通过基类指针删除。
  - 配套易错点：**构造函数与析构函数中调用虚函数不会发生多态**——此时对象的动态类型是"正在构造/析构的那一层"，虚表尚未（或已不再）指向派生类版本。
- 调用顺序：**构造先基类后派生**（虚基类由最底层派生类直接调用）；**析构先派生后基类**（与构造相反）。

### 2.4.6 初始化成员列表（哪些情况必须用）

- 初始化**引用类型成员**（引用必须在创建时绑定，不能重新赋值）。
- 初始化 **const 成员**（只能在初始化时赋值）。
- 初始化**无默认构造函数的类成员**（必须显式调用带参构造）。
- 调用**基类的非默认构造函数**。
- 注意：初始化列表的执行发生在对象构造阶段；成员初始化顺序由**类中声明顺序**决定，与初始化列表书写顺序无关。

### 2.4.7 友元

- 友元打破封装：允许外部类或函数访问当前类的 private/protected 成员。
- **单向性**：A 声明 B 为友元，B 可以访问 A 的私有成员，但 A 不能访问 B 的私有成员。
- 使用场景：运算符重载（如流运算符）、工具函数访问私有数据。

### 2.4.8 抽象类与纯虚函数

- 抽象类：包含**至少一个纯虚函数**的类，不能实例化，只能作为基类。
- 派生类必须实现所有纯虚函数，否则仍是抽象类。
- 抽象类的**析构函数应为虚函数**。

```cpp
class Shape {                       // 抽象类
public:
    virtual double area() const = 0; // 纯虚函数
    virtual void draw() const {}     // 普通虚函数（可选默认实现）
};
```

### 2.4.9 运算符重载

- 意义：增强抽象性、提升可读性、简化逻辑、支持泛型。
- **不允许重载的 5 个运算符**：`::`（作用域）、`.`（成员访问）、`.*`（成员指针访问）、`?:`（三目）、`sizeof`（均不可重载）。
- 三种方式：成员函数、全局函数（非成员）、友元函数。
- **流运算符（`<<`/`>>`）不便用成员函数重载**（**注意：不是"不能"**，用成员函数在语法上是合法的）：成员重载隐含左操作数是当前类对象，调用形式会变成"对象 << 流对象"，与常规写法 `cout << obj` 相反。解决：重载为**非成员（通常友元）函数**——左操作数是流对象，写法自然。作数为流对象引用，右操作数为自定义类对象。
- 流运算符重载返回引用：为了支持**链式调用**（`cout << a << b`）并避免不必要的复制。

### 2.4.10 继承的优缺点

- **优点**：代码复用；层次化建模表达 is-a 关系；虚函数实现运行时多态；接口抽象符合开闭原则。
- **缺点**：子类与父类紧耦合，父类修改影响所有子类；多重继承/深层继承链复杂（菱形继承）；破坏封装（子类依赖父类 protected 细节）；方法污染（被迫继承不需要的方法）；继承关系编译期固化，动态扩展不如组合灵活。

### 2.4.11 设计不能被继承的类

- C++11 起用 `final` 关键字：`class B final : public A {}`。
- 经典做法：私有构造函数 + 静态工厂方法（无法被继承实例化）。

## 2.5 多态

### 2.5.1 静态多态与动态多态

- **静态多态（编译时）**：函数重载、运算符重载、模板。
- **动态多态（运行时）**：虚函数 + 继承，运行时通过虚表确定调用目标。

### 2.5.2 虚函数实现原理（VTable / vptr）

1. **虚函数表（VTable）**：每个含虚函数的类对应一张表，是**函数指针数组**，每个条目对应一个虚函数；编译器编译期生成，存放于只读数据段。
2. **虚表指针（vptr）**：每个对象内存布局中有一个隐式指针指向所属类的 VTable。
3. 派生类重写虚函数 → VTable 对应条目指向派生类实现；未重写 → 仍指向基类实现。
4. 调用虚函数时通过对象 vptr → VTable → 函数指针，实现**动态绑定**。

### 2.5.3 重载、重写、隐藏的区别

| 概念 | 条件 | 绑定 |
| --- | --- | --- |
| 重载（Overload） | 同一作用域、函数名相同、参数列表不同（与返回值无关） | 静态绑定（编译期） |
| 重写（Override） | 派生类重定义基类**虚函数**，返回值与参数列表一致 | 动态绑定（运行时，通过虚表） |
| 隐藏（Hiding） | 基类函数非虚但派生类同名；或基类虚函数但参数不同 | 静态绑定，子类同名函数屏蔽父类版本 |

### 2.5.4 子类覆盖函数不加 virtual 是否还能多态？

- **能**。虚函数的特性会**隐式继承**到子类的覆盖函数中——子类重写基类虚函数即使不写 `virtual`，该函数仍是虚函数，通过虚表动态绑定实现多态（与是否显式加 virtual 无关）。

### 2.5.5 虚函数与普通成员函数的存储位置

- 虚函数表（VTable）与函数代码存放在**只读代码段/数据段**；vptr 存放在**对象内部**（通常对象内存布局首部）。
- 普通成员函数代码同样在代码段；对象中不存储普通函数。

## 2.6 C++11 与工程实践

### 2.6.1 右值引用、移动语义与完美转发（★★★★ C++11 第一必考）

**要解决什么问题**：函数返回或按值传递大对象（`vector`、`string`）时，若只能"深拷贝"，就要**重新分配内存 + 逐个元素复制**再销毁源对象——纯属浪费。移动语义让"即将销毁的临时对象"把**资源所有权直接移交**过去，复杂度从 O(n) 降到 O(1)。

**左值与右值**：

| | 左值（lvalue） | 右值（rvalue） |
| --- | --- | --- |
| 直观判断 | **能取地址**、有名字、有持久身份 | 临时对象、字面量、**不能取地址** |
| 例子 | 变量 `a`、`*p`、`arr[0]`、返回引用的函数 | `1`、`a + b`、`foo()`（返回非引用）、`std::move(a)` |
| 绑定 | 非 const 左值引用 `T&` 只能绑左值 | 右值引用 `T&&` 只能绑右值 |
| 生命周期 | 超出作用域才结束 | 通常在**表达式结束时**销毁 |

- **`T&&` 的两副面孔（最易混）**：
  - 用在**具体类型**上：`int&& r = 42;` → 右值引用，**只能绑右值**；
  - 用在**模板参数**上：`template<class T> void f(T&& x)` → **万能引用（forwarding reference）**，既能绑左值也能绑右值。这是推导语境决定的；`const T&&`、`std::vector<T>&&` 都**不是**万能引用。

**移动构造与移动赋值**：

```cpp
class Buffer {
  char* data_; size_t n_;
public:
  // 拷贝：深复制，O(n)
  Buffer(const Buffer& o) : data_(new char[o.n_]), n_(o.n_) { std::copy(o.data_, o.data_ + o.n_, data_); }
  // 移动：只"偷"指针，O(1)；参数是右值引用，且必须 noexcept（否则 vector 扩容不敢用）
  Buffer(Buffer&& o) noexcept : data_(o.data_), n_(o.n_) { o.data_ = nullptr; o.n_ = 0; }
  Buffer& operator=(Buffer&& o) noexcept {
    if (this != &o) { delete[] data_; data_ = o.data_; n_ = o.n_; o.data_ = nullptr; o.n_ = 0; }
    return *this;
  }
  ~Buffer() { delete[] data_; }
};
```

- **关键点**：
  1. **"移动"没有语言层面的魔法**——它就是"偷资源 + 把源对象置为可析构的安全状态"（通常置空）；**忘记置空会导致双重释放**。
  2. **`noexcept` 很重要**：`std::vector` 扩容时若移动构造可能抛异常，为满足强异常保证就**只能退回拷贝**，性能直接退化。
  3. **被移动对象仍然合法但值未指定**，只能"赋新值或析构"，不要读它的内容。
  4. **Rule of Five**：一旦自定义了析构/拷贝构造/拷贝赋值/移动构造/移动赋值中的任何一个，通常五个都要考虑（呼应 §2.4.3 的默认函数说明）。

**`std::move` 与 `std::forward` 的区别（必考）**：

- **`std::move(x)` 不移动任何东西**——它只是一个**类型转换**（`static_cast<T&&>(x)`），把左值"标记"成右值，从而能匹配到移动构造；真正移动的是随后调用的移动构造函数。
- **`std::forward<T>(x)`** 用于模板中**保持参数的原始值类别**：左值进来仍是左值、右值进来仍是右值。它是"完美转发"的关键。
- **经典错误**：在转发函数里用 `std::move` 代替 `std::forward`，会把调用者传入的**左值**也当右值移走，导致调用方的对象被"掏空"。

```cpp
template <class T>
void wrapper(T&& x) {
  target(std::forward<T>(x));   // 正确：左值转发为左值，右值转发为右值
  // target(std::move(x));      // 错误：左值参数也会被移走
}
```

**返回值优化与移动的关系（追问点）**：

- **RVO/NRVO**：编译器可直接在调用方空间构造返回对象，**连移动都省掉**（C++17 起对返回纯右值是**强制**的）。
- 所以"返回局部对象时写 `return std::move(x);`"是**反优化**——它会阻止 NRVO，反而多一次移动。**直接 `return x;`**。
- 优先级：**NRVO > 移动构造 > 拷贝构造**；C++17 之后很多场景连移动都不会发生。

### 2.6.2 auto、四种 cast 与范围 for

- `auto`：类型推导；`auto` 作返回值（C++14 起）需与模板/decltype 配合使用。
  - 注意 `auto` 会**丢弃引用与顶层 const**（`auto x = vec[0];` 是拷贝！要引用得写 `auto&`），这是常见性能陷阱。
- 四种 cast：
  - `static_cast`：编译期类型转换（一般类型转换、数值转换、向上转型）。
  - `dynamic_cast`：运行时安全检查（多态类型向下转换，失败返回 nullptr / 抛 `std::bad_cast`）；**要求基类有虚函数**。
  - `const_cast`：去除/添加 const（**唯一**能去除 const 的转换）。
  - `reinterpret_cast`：底层位模式重新解释（危险，慎用）。
- 智能指针：`unique_ptr` / `shared_ptr` / `weak_ptr`（见 §2.1.5）。
- 范围 for：`for (auto& x : container)` 底层是迭代器循环；**遍历中增删元素会使迭代器失效**（§2.1.3 的容器失效规则同理）。

### 2.6.3 模板基础、特化与 SFINAE（★★ 中高频）

- **模板的作用**：把"类型"参数化，实现**编译期多态**（与虚函数的运行期多态相对，§2.5.1）；代价是代码膨胀（每种类型实例化一份）与编译变慢。
- **实例化**：模板本身不是代码，只有被**具体类型使用**时才生成代码（隐式实例化）；也可显式实例化 `template class Foo<int>;`（常用于把实现藏进 .cpp、减少编译时间）。
- **特化**：

| 形式 | 写法 | 说明 |
| --- | --- | --- |
| 全特化 | `template<> class Foo<int> { ... };` | 为**某个具体类型**单独实现 |
| 偏特化 | `template<class T> class Foo<T*> { ... };` | 为**一类类型**（如所有指针）单独实现；**函数模板不支持偏特化**（只能靠重载） |
| 类型萃取（traits） | `std::is_pointer<T>::value`、`std::enable_if` | 用特化在**编译期**做类型判断与分支 |

- **SFINAE**（Substitution Failure Is Not An Error）：模板参数替换失败**不算错误**，只是该重载被移出候选集。它是"按类型选择不同实现"的传统手段：

```cpp
// 只对整型启用这个重载（C++11 写法）
template <class T>
typename std::enable_if<std::is_integral<T>::value, void>::type
process(T v) { /* 整型专用实现 */ }
```

- **现代替代**：C++17 的 `if constexpr`（编译期分支，比 SFINAE 可读得多）、C++20 的 **concepts**（直接写约束 `template<std::integral T>`，报错信息也友好）。面试若问"SFINAE 现在还用吗"，答"**新代码优先用 `if constexpr` / concepts，SFINAE 主要用于读老代码与库实现**"。
- **`decltype` 与 `auto` 的配合**：`decltype(expr)` 精确取表达式类型（保留引用与 cv 限定），`auto` 会丢弃它们；需要保持引用要写 `decltype(auto)` 或 `auto&&`。

### 2.6.4 常用设计模式

- **单例**：全局唯一实例，全局访问点（注意线程安全、生命周期）。
- **工厂**：将对象创建逻辑与使用逻辑解耦（简单工厂、工厂方法、抽象工厂）。
- **代理**：为对象提供替身，控制访问（延迟加载、权限控制）。
- **适配器**：将不兼容的接口转换为客户端期望的接口。

### 2.6.5 多线程与内存序（★★ 加分项）

- **`std::thread` 基础**：`std::thread t(f, args...)` 创建即启动；**必须 `join()` 或 `detach()`**，否则析构时 `std::terminate`。`std::jthread`（C++20）析构自动 join。
- **四种同步手段**：`std::mutex` + `lock_guard`/`unique_lock`、`std::condition_variable`（配 `unique_lock`，`wait` 要传谓词防虚假唤醒）、`std::atomic`、`std::call_once`（单例初始化）。
- **`volatile` 不是线程同步工具**（§2.3.4）：它只阻止编译器优化掉访问，**不保证原子性与可见性顺序**。要跨线程共享就用 `std::atomic` 或加锁。
- **内存序（memory order）—— 面试的深水区**：

| 内存序 | 语义 | 代价 |
| --- | --- | --- |
| `seq_cst`（默认） | 全局单一顺序，最强保证，最好推理 | 最慢（可能插入内存栅栏） |
| `acquire` / `release` | **配对使用**：release 之前的写，对 acquire 之后的读可见；用于实现"发布-订阅"式传递 | 中等 |
| `relaxed` | 只保证该操作本身原子，**不保证任何跨线程顺序** | 最快，但极易写错 |
| `acq_rel` | 读改写操作（如 `fetch_add`）同时具备两者 | — |

- **典型用法（release/acquire 配对）**：

```cpp
std::atomic<bool> ready{false};
int data = 0;
// 线程 A
data = 42;
ready.store(true, std::memory_order_release);   // 保证 data 的写在 store 之前对其他线程可见
// 线程 B
while (!ready.load(std::memory_order_acquire)) {}  // 看到 true 之后
assert(data == 42);                                 // 一定能读到 42
```

- **为什么需要内存序**：CPU/编译器会**重排**指令（§4.3.4 的缓存一致性与 store buffer 导致），没有内存序约束时，"数据写好了但标志位先被看到"会发生。**默认 `seq_cst` 最安全**；只在性能敏感的库代码里才降级到 acquire/release，`relaxed` 必须配合明确的算法推理。
- **与"无锁编程"的关系**：CAS（§4.3.5）只保证单点原子，**无锁容器的正确性依赖内存序**——这也是无锁编程难写、难调的根本原因。

### 2.6.6 STL 容器特性与迭代器失效（★★ 高频）

**容器选择速查**：

| 容器 | 底层 | 随机访问 | 插入/删除 | 迭代器失效规则 |
| --- | --- | --- | --- | --- |
| `vector` | 连续数组 | O(1) | 尾部均摊 O(1)，中间 O(n) | **扩容时全部失效**；`insert/erase` 后**该位置及之后**失效 |
| `deque` | 分段连续 | O(1) | 头尾 O(1) | `push` 头尾会使**迭代器**失效但**引用**仍有效 |
| `list` / `forward_list` | 双向/单向链表 | 不支持 | 已知位置 O(1) | **只有被删除元素的迭代器失效** |
| `map` / `set` | 红黑树 | 不支持（有序） | O(log n) | 只有被删除元素的失效 |
| `unordered_map` / `set` | 哈希表 | 不支持 | 平均 O(1) | **rehash 时全部失效**（`rehash` 由负载因子触发，可 `reserve` 预防） |
| `string` | 连续（可能有 SSO） | O(1) | 尾部均摊 O(1) | 同 `vector` |

- **`vector` 是最该记住的**：**扩容会重新分配并把元素搬走**，所有指针/引用/迭代器全部失效；因此"边遍历边 `push_back`"是经典 bug。预防：先 `reserve(n)`。
- **`vector<bool>` 是特化**：按位压缩存储，**不是真正的 `bool` 数组**，`operator[]` 返回代理对象、不能取地址、`data()` 不可用——踩过才知道。
- **`map` vs `unordered_map`**：需要**有序遍历/范围查询**用 `map`；纯查找用 `unordered_map`，但要注意哈希质量与 rehash 开销；游戏里高频查找常自研开放寻址哈希表以避免节点分配。
- **`erase` 的正确写法**：

```cpp
for (auto it = m.begin(); it != m.end(); ) {
  if (needRemove(*it)) it = m.erase(it);   // erase 返回下一个有效迭代器
  else                ++it;
}
```

- **分配器与性能**：频繁小块分配是主要开销来源，工程上常用**内存池/对象池**（§2.1.5、§2.6.8）或 `pmr`（C++17 多态分配器）替代默认 `new/delete`。

### 2.6.7 `shared_ptr` 的线程安全边界（★ 容易答错）

- **`shared_ptr` 的引用计数是原子的**：多个线程各自持有**不同**的 `shared_ptr` 实例、对同一个对象做拷贝/析构 → 安全。
- **但被指向的对象不是线程安全的**：多线程同时读写 `*p` 仍需自己加锁。
- **同一个 `shared_ptr` 实例被多线程同时读写 → 不安全**：比如一个线程 `p = q`（改写指针本身）、另一个线程读 `p`，会数据竞争。要用 `std::atomic<std::shared_ptr<T>>`（C++20）或加锁。
- **控制块与 `make_shared`**：`make_shared` 把对象与控制块**一次分配**（少一次分配、缓存更友好），代价是**对象内存要等 `weak_ptr` 也释放才能回收**；`shared_ptr<T>(new T)` 是两次分配。
- **循环引用 → 内存泄漏**：两个对象互相 `shared_ptr` 会永远不释放；解法是**一方改用 `weak_ptr`**，用前 `lock()` 提升。这是面试必问的"shared_ptr 会不会泄漏"的标准答案。
- **`enable_shared_from_this`**：类内需要拿到自身的 `shared_ptr` 时必须继承它并调用 `shared_from_this()`；**不能在构造函数里调用**（此时控制块还没建立）。

### 2.6.8 提高 C++ 性能的手段（常见追问）

- 减少临时对象：返回值优化（RVO/NRVO）、移动语义（§2.6.1）、`operator=` 复用。
- 内联与去虚化：小函数内联、`final`/LTO 让虚调用去虚化。
- **函数指针 vs 函数对象 vs `std::function` 的取舍**：`std::function` 有**类型擦除开销、可能堆分配、通常比裸函数指针或模板仿函数更慢**——它换来的是"能存任意可调用对象"的灵活性。**热路径优先模板仿函数（编译期内联）或裸函数指针；需要运行时多态与存储时才用 `std::function`**。
- 内存池、对象池；缓存友好（数据局部性，§4.3.4）；预计算；延迟计算。
- 高效数据结构（`vector` 预留容量、`map` 换 `unordered_map`、避免 `vector<bool>` 等）。
- 减少拷贝：按 `const&` 传参、用 `emplace_back` 代替 `push_back(T(...))`、`reserve` 预防扩容与迭代器失效（§2.6.6）。

## 2.7 其他高频考点

### 2.7.1 sizeof 与 strlen

- `sizeof`：编译期运算符，求**类型或变量占用字节数**（含字符串的 `\0`，数组不退化）。
- `strlen`：运行时函数，求字符串**字符个数**（不含 `\0`），遇到 `\0` 停止。

### 2.7.2 strcpy、sprintf 与 memcpy 的区别

- `strcpy`：字符串拷贝，遇 `\0` 停止；不检查目标缓冲区大小，易溢出。
- `sprintf`：格式化输出到字符串缓冲区（`snprintf` 更安全）。
- `memcpy`：按字节数拷贝内存（不关心内容），需指定长度，效率高。

### 2.7.3 位操作：某位清 0 / 置 1

```cpp
void clear_bit(unsigned int *x, int n) { *x &= ~(1U << n); }  // 第 n 位清 0
void set_bit(unsigned int *x, int n)   { *x |= (1U << n); }   // 第 n 位置 1
```

### 2.7.4 全局变量与局部变量的内存区别

- 全局变量/静态变量：静态存储区，程序启动时分配，生命周期为整个程序。
- 局部变量：栈上，函数调用时分配、返回时自动释放。
- 同名时局部变量遮蔽（Shadowing）全局变量，在其作用域内可见。

### 2.7.5 堆栈溢出一般由什么导致

- 递归过深（无终止条件或深度过大）。
- 局部变量过大（大数组/大对象分配在栈上）。
- 栈上动态分配过多（alloca 等）。

### 2.7.6 Debug 与 Release 版本的区别

- Debug：含调试信息，未优化，便于断点调试，运行慢、体积大。
- Release：编译器优化，无调试符号，运行快、体积小，行为可能与 Debug 不同（如未定义行为更明显）。

### 2.7.7 其他零散考点（速记）

- `#include <filename.h>` 搜索系统/标准库路径；`#include "filename.h"` 先搜索当前工程路径。
- `#error` 的作用：编译期输出错误信息并终止编译（如 `#if !defined(...) #error ...` 防止头文件重复包含的宏保护）。
- `switch` 参数必须是**整型或枚举类型**（不能是浮点、字符串）。
- `char`/`int`/`float`/`double` 在 Win32 下分别占 1/4/4/8 字节。
- 字符常量（`'A'`）sizeof 为 1；字符串常量（`"A"`）sizeof 为 2（含 `\0`）。
- 死循环写法：`for(;;)` 或 `while(1)`。
- 声明与定义：声明不分配空间、可多次；定义分配空间、只能一次。
- 变量声明 `short i = 0; i = i + 1L;`：i 是 short，+1L（long）结果先提升为 long，赋值回 short 可能**截断/警告**（依赖值是否超范围）。
- `&&`/`||` 有短路求值；`&`/`|` 是按位运算（无短路）。
- 静态库（.a/.lib）：链接时被复制进可执行文件；动态库（.so/.dll）：运行时加载共享（省内存、可热更新）。
- `main` 函数执行前：全局/静态对象构造、库初始化等。
- struct 与 union：union 所有成员共享同一块内存，同一时刻只能存其中一个成员。
- assert：调试期断言，条件为假时中止程序；Release 编译可关闭（NDEBUG）。
- 字符串转数字：`strtol(str, &endptr, 10)` 或 C++11 `std::stoi` / `std::stod`。
- 判断两个平面是否相交（不用碰撞体）：用平面方程比较法向量与点距，或求解两平面方程组看是否有解。

## 2.8 零散补充题（C++ 面试题 docx 收录）

- **成员函数靠什么区分不同对象的成员数据？** → **this 指针**：每个非静态成员函数调用时，编译器自动传入一个指向当前对象的指针（this）；不同对象的成员变量在内存中独立存储，通过 this 定位到各自的数据。
- **在类内部定义成员函数的函数体，该函数具备什么属性？** → 编译器会将其视为**内联函数**（隐式 inline）。
- **常对象（const 对象）**：被 `const` 修饰的类对象；其非 mutable 成员变量不可修改，只能调用**常成员函数**，必须通过构造函数在定义时初始化。
- **IP 地址的编码分为哪两部分？** → **网络部分**（网络号，标识所在网络）和**主机部分**（主机号，标识网络内主机），子网掩码用于划分两者。
- **何时需要预编译？** → ① 头文件包含大量稳定代码时用**预编译头（PCH）**减少重复编译时间；② 用条件编译宏（`#ifndef` 等）防止头文件重复包含；③ 平台差异代码用 `#ifdef _WIN32` 等条件编译。
- **对象之间怎样实现数据共享？** → 通过**静态成员变量**（属于类、所有实例共享一份），或通过指针/引用传递同一个对象。
- **构造函数和析构函数何时被调用？是否需要手工调用？** → 栈对象：作用域进入/退出时自动调用；堆对象：`new`/`delete` 时自动调用。**一般不需要手工调用**；仅在 `placement new`（显式构造）、显式析构（`obj.~T()`，配合定位 new 使用）等特殊场景才手工调用。
- **define 与 const 的区别**：`#define` 是**预处理期文本宏替换**，无类型检查、无作用域、不占内存（编译后不存在）；`const` 是**编译期常量**，有类型检查、遵守作用域规则、占用存储（或编译期折叠）。
- **简述枚举类型（enum）**：定义一组具名的整型常量（枚举成员），默认从 0 开始递增，可显式指定值；C++11 强类型枚举 `enum class` 更安全（需显式作用域、不隐式转 int）。
- **全局变量的优缺点**：优点——全局可见、方便共享、生命周期贯穿程序；缺点——破坏封装、易命名冲突、难以追踪修改、多线程不安全、增加耦合。
- **类的声明与实现分开的好处**：降低编译依赖（改动实现无需重新编译所有使用者）、接口与实现解耦、便于团队协作与库发布（二进制兼容）、隐藏实现细节。
- **QT 信号槽机制（简述）**：信号（signal）与槽（slot）通过 `connect` 连接；对象状态变化时发射信号，框架调用已连接的槽函数——本质是**类型安全的回调/观察者机制**，解耦发送方与接收方（线程安全的队列连接方式可跨线程）。
- **boost 常用类**：`thread`（线程）、`asio`（网络/异步 IO）、`signal`（信号槽）、`bind`/`function`（函数对象封装，C++11 已并入标准库）、`smart_ptr`（智能指针，已并入标准库）。
