# 四、操作系统与计算机基础

> 本章是 Unity/C# 客户端岗位的**通用基础轮**：进程/线程/协程、同步与死锁、内存与缓存、IPC、IO 模型。
> 与项目联动：网络消息队列（§4.1 的 CAS 无锁队列）、战斗逻辑线程模型（§4.2）、AB 加载的 IO 模型（§4.6）。

## 4.1 进程、线程、协程

### 4.1.1 概念对比

| 对比项 | 进程 | 线程 | 协程 |
| --- | --- | --- | --- |
| 定义 | 操作系统**资源分配**的基本单位；程序运行后形成的独立内存体 | 进程内的执行单元，操作系统**调度**的最小单位 | 用户态的轻量级"线程"，由程序控制调度 |
| 资源 | 独立的内存空间、地址空间、堆 | 共享进程内存；拥有独立栈、共享堆 | 单线程内并发（交替执行），共享状态无需加锁 |
| 调度 | 操作系统 | 操作系统 | 程序自身（协作式） |
| 开销 | 创建/切换/销毁开销大 | 比进程小 | 极小 |
| 通信 | IPC（管道、消息队列、共享内存等，详见 §4.5） | 直接共享内存，需同步（锁） | 共享宿主线程上下文 |
| 隔离 | 进程间相互隔离，一个崩溃不影响其他 | 一个线程崩溃可能影响进程 | — |
| 切换方式 | 抢占式 | 抢占式 | 主动让出（yield） |

### 4.1.2 详细说明

**三个核心概念（区别）**：

- **串行**：任务排队执行、互不重叠，前一个完全结束才开始下一个。
- **并发**：任务交错推进、宏观同时进行，单核即可实现；进程间、线程间均为并发（单核时间片交替、多核并行），绝非串行。
- **并行**：同一时刻真正同时执行，需多核。

**进程 / 线程 / 协程**：

- **进程**：程序运行实例（≈ 一个应用程序），OS 以进程为单位分配资源（CPU 时间片、内存）；进程间相互隔离。
- **线程**：进程内的执行单元，不能独立存在；一个进程含多线程；拥有独立栈、共享进程内存，执行不同任务，需同步（锁）。
- **协程**：用户态轻量执行流，程序显式调度（yield/await 挂起恢复），同一线程内交替执行 = 协作式并发（非并行，任一时刻仅一个在执行）；共享堆、各自独立栈；单线程内共享状态无需加锁；Unity 中运行在主线程。
- **为什么"线程崩溃会影响整个进程"**：同一进程的线程**共享地址空间**，一个线程野指针写坏堆/栈，其它线程与进程整体都可能崩溃；而进程间有独立地址空间，OS 会隔离故障。

**线程与进程的取舍**：

| | 进程 | 线程 |
| --- | --- | --- |
| 创建/切换成本 | 高（切页表、刷 TLB） | 低（同地址空间，只切栈与寄存器） |
| 通信成本 | 高（需 IPC 拷贝或映射） | 低（直接读写共享内存） |
| 容错 | 好（互相隔离） | 差（共享地址空间） |
| 适用 | 需要隔离、稳定性优先（Chrome 多进程、服务器多进程模型） | 需要频繁通信、高并发计算（Job System 线程池） |

### 4.1.3 进程控制块（PCB）

PCB 是操作系统内核存储进程状态及相关信息的数据结构，包含：

- 进程标识符（进程 ID、父进程 ID 等）；
- 进程状态（运行中、就绪、阻塞等）；
- 处理机状态（寄存器内容、程序计数器、状态寄存器等）；
- 进程调度信息（优先级、时间片、等待时间）；
- 内存管理信息（页表基址、段表、界限寄存器）；
- IO 状态信息（打开文件表、设备分配情况）。

### 4.1.4 进程状态与转换（★ 常考）

**五态模型**（面试答五个即可，七态是加了挂起）：

| 状态 | 含义 |
| --- | --- |
| 新建（New） | 进程正在被创建，尚未进入就绪队列 |
| 就绪（Ready） | 已获得除 CPU 外的所有资源，等待调度 |
| 运行（Running） | 已获得 CPU，正在执行（单核同一时刻仅一个） |
| 阻塞（Blocked/Waiting） | 因等待某事件（IO 完成、信号量、睡眠）而暂停 |
| 终止（Terminated） | 执行完毕或被终止，等待回收资源 |

**合法转换（箭头是不会出现的转移就是错的）**：

```
        创建            调度              时间片用完 / 被抢占
New ────────→ Ready ──────────→ Running ──────────────→ Ready
                 ↑                  │
                 │                  │ 等待事件（IO/锁/信号量）
                 │                  ↓
                 └──── 事件完成 ── Blocked
                                    │
        Running ── 退出/被杀死 ──→ Terminated
```

三个**高频陷阱**：

- **阻塞 → 运行 不存在**：阻塞的进程等到事件后只能进入**就绪**，还要再等调度；"被唤醒后立刻执行"是错的。
- **就绪 → 阻塞 不存在**：没拿到 CPU 就不可能去发起等待。
- **时间片用完是 运行 → 就绪**（不是阻塞），因为进程仍具备运行条件。

## 4.2 线程同步

### 4.2.1 同步原语

- **锁（Lock/Mutex）**：互斥访问临界区，保证同一时刻只有一个线程进入。互斥量有"所有权"概念（谁加锁谁解锁）。
- **信号量（Semaphore）**：控制同时访问资源的线程数量（计数信号量可 >1）。`P` 操作申请（减 1，为负则阻塞）、`V` 操作释放（加 1，唤醒等待者）——**可用于互斥（初值 1），也可用于同步/限流（初值 N）**。
- **互斥与同步**：互斥解决"竞争"（数据竞争），同步解决"协作"（执行顺序）。
- **条件变量/事件**：线程间通知机制。**条件变量必须与互斥量配合**，且等待要用 `while` 而非 `if` 判断条件（防止虚假唤醒）。
- **读写锁（Read-Write Lock）**：读读不互斥、读写/写写互斥。适合**读多写少**；注意写者饥饿问题。
- **自旋锁（Spinlock）**：不睡眠、忙等重试，适合**临界区极短**且不希望线程切换开销的场景；临界区长会白烧 CPU。Unity 的 `Job System`/`NativeContainer` 属于无锁/受限并发模型，**不能**在 Job 里随意加托管锁。
- **无锁队列**：基于 **CAS（Compare And Swap）** 等原子操作实现，避免锁竞争，适用于高频读写场景（如游戏网络消息队列）。

### 4.2.2 经典同步问题（面试手写高发）

- **生产者-消费者**：一个互斥量保护缓冲区 + 两个信号量（`empty`、`full`）。**必须先 P 资源信号量再 P 互斥量**，否则死锁。
- **读者-写者**：读优先（写者可能饿死）或写优先（用额外信号量排队），考点在"为什么会产生饥饿"。
- **哲学家就餐**：5 人 5 筷。破坏死锁的方法——① 最多允许 4 人同时拿筷；② 奇数号先拿左、偶数号先拿右（破坏循环等待）；③ 一次拿两只（用互斥量把拿筷变成原子操作）。
- **银行家算法**：见 §4.5.2。

### 4.2.3 死锁（★★★★ 必考）

**定义**：多个进程因竞争资源而互相等待对方释放，导致**永久阻塞**。

**四个必要条件（缺一不可，破坏其一即可预防）**：

| 条件 | 含义 | 破坏手段 |
| --- | --- | --- |
| 互斥 | 资源同一时刻只能被一个进程占用 | 尽量让资源可共享（如只读数据） |
| 占有并等待 | 持有至少一个资源，又在等待别的资源 | **一次性申请全部资源**（破坏"等待"） |
| 不可剥夺 | 已获得的资源不能被强行夺走 | **允许剥夺**：申请不到就释放已有资源 |
| 循环等待 | 存在进程-资源的环形等待链 | **资源有序分配**：所有进程按同一顺序申请 |

> 记忆口诀：**互斥、占有等待、不可剥夺、循环等待**——"互占不循"。
> **破坏"互斥"通常做不到**（锁的本质就是互斥），所以工程上最常用的是**破坏循环等待（统一加锁顺序）**——这也是"为什么规定锁顺序"的面试答案。

**四种处理策略**：

1. **预防（Prevention）**：从设计上破坏四个必要条件之一，代价是降低资源利用率。
2. **避免（Avoidance）**：运行时判断分配是否安全，只在不进入不安全状态时分配——**银行家算法**。
3. **检测与恢复（Detection & Recovery）**：允许死锁发生，用资源分配图找环，然后杀进程/回滚。
4. **鸵鸟策略**：不处理，靠重启（多数通用 OS 的实际选择）。

**银行家算法（要点）**：

- 数据结构：`Available`（可用）、`Max`（最大需求）、`Allocation`（已分配）、`Need = Max − Allocation`。
- 每次请求先做**试探性分配**，再跑**安全性算法**：找一个 `Need ≤ Available` 的进程，假设它执行完并归还资源，重复；若所有进程都能被"收尾"，则存在**安全序列**，分配可行，否则回退。
- 关键词：**安全状态 ≠ 无死锁**，而是"存在一种调度顺序使所有进程都能完成"。

**死锁 vs 饥饿 vs 活锁（易混）**：

- **死锁**：互相等待，**永远不会**推进（循环等待）。
- **饥饿**：某个进程**长期拿不到资源**（如低优先级一直被高优先级抢占），但系统整体在推进。
- **活锁**：进程**一直在改变状态却无进展**（如两个线程都退让重试），没有阻塞但也没前进。

**排查思路（工程题）**：看线程栈是否卡在锁上 → 找出持锁者与等待者的**环路** → 核对是否存在"加锁顺序不一致"或"持锁做耗时操作/回调"。**实践建议**：统一加锁顺序、缩短持锁时间、不在持锁时调用外部回调（易反向加锁）、必要时用超时锁（`tryLock`）兜底。

## 4.3 内存管理

### 4.3.1 进程内存布局

- **栈（Stack）**：函数调用相关，局部变量/参数/返回地址，自动分配释放，空间小但快，**向下增长**。
- **堆（Heap）**：动态申请（new/malloc），需手动释放，空间大但慢，易产生碎片和泄漏，**向上增长**。
- **静态区（数据段 + BSS）**：全局变量、静态变量。已初始化在数据段、未初始化在 BSS。
- **常量区（只读数据段）**：字符串字面量、`const` 全局量。
- **代码段（Text）**：可执行指令，通常只读、可共享。
- **堆栈溢出原因**：递归过深、局部变量过大（栈上大数组）、栈上分配过多。
- **内存分配方式**：静态分配（编译期确定）、栈上自动分配、堆上动态分配。

### 4.3.2 虚拟内存与分页（★★★ 高频）

- **为什么需要虚拟内存**：① 进程隔离（各自独立地址空间，互不越界）；② 允许**部分装入**即可运行，程序可大于物理内存；③ 便于共享与写时复制。
- **地址翻译**：CPU 发出**虚拟地址** → MMU 查**页表**得物理页框号 → 拼出**物理地址**。页表项含有效位、读写权限、脏位、访问位等。
- **缺页中断**：访问的页不在内存 → 触发中断 → OS 从磁盘换入 → 更新页表 → 重新执行指令（对进程透明）。
- **多级页表**：解决页表本身过大（32 位 4KB 页、4GB 空间 → 单级页表 4MB/进程）。分级后**只为实际用到的区域建表**，省内存，代价是多次访存（用 TLB 缓解）。
- **TLB（快表）**：页表项的硬件缓存。命中则无需访存查表；**进程切换要刷 TLB**（或加 ASID 标记），这也是进程切换比线程切换贵的原因之一。

**页面置换算法（必背对比）**：

| 算法 | 规则 | 特点 |
| --- | --- | --- |
| OPT（最佳） | 淘汰**未来最久不用**的页 | 缺页率最低，但**无法实现**（需预知未来），只作理论上界 |
| FIFO | 淘汰**最先进入**的页 | 简单；会出现 **Belady 异常**（物理块增多缺页反而变多） |
| **LRU** | 淘汰**最久未使用**的页 | 性能接近 OPT；需维护访问顺序，硬件开销大（近似实现：Clock） |
| Clock（二次机会） | 环形扫描，访问位为 1 则清零并跳过，为 0 则淘汰 | LRU 的廉价近似，实际系统常用 |
| LFU | 淘汰**访问次数最少**的页 | 关注频率而非时间；新页易被淘汰（需老化处理） |

- **Belady 异常**：只有 FIFO 这类"未考虑历史访问"的算法会出现；LRU/OPT 属于**栈式算法**，不会出现。
- **抖动（Thrashing）**：多道程序度过高，页频繁换入换出，CPU 大量时间耗在换页上。解决：降低并发度、增大内存、用**工作集（Working Set）**模型分配页框。

### 4.3.3 内存对齐与结构体大小（★ 常考）

- **为什么要对齐**：CPU 按字长批量读内存，**未对齐的访问可能跨越两个内存字**，需要多次访存甚至触发异常；对齐后一次读取即可。
- **对齐规则**（x86/ARM 常见约定）：
  1. 每个成员的偏移量必须是 **`min(成员自身大小, 编译器对齐系数)`** 的整数倍，必要时填充（padding）；
  2. 结构体总大小必须是**最大成员对齐值**的整数倍，末尾补齐（trailing padding）；
  3. 可用 `#pragma pack(n)` / `alignas` 强制改变对齐（**pack(1) 即取消填充**，代价是访问变慢）。
- **示例**：`struct { char a; int b; char c; }` 在 4 字节对齐下大小为 **12**（a 占 1 + 填 3 + b 占 4 + c 占 1 + 末尾填 3），而非 6。
- **优化技巧**：把成员**按大小从大到小排列**可减少填充（上例改成 `int b; char a; char c;` 则为 8 字节）。这也是游戏里"热数据紧凑排列"的同一个道理（§4.3.4）。
- **Unity/C# 相关**：`Marshal.SizeOf` 与 `sizeof` 在含引用字段时不同；`[StructLayout(LayoutKind.Sequential, Pack = 1)]` 用于与 C/C++ 或网络协议对接时**控制布局**；`MemoryPack` 序列化也依赖确定的字段布局。

### 4.3.4 CPU 缓存与伪共享（★★ 加分项）

- **存储层次**：寄存器 → L1（分指令/数据，~几十 KB）→ L2（~几百 KB）→ L3（共享，数 MB~数十 MB）→ 主存 → 磁盘。越靠近 CPU 越快越小越贵。
- **局部性原理**：**时间局部性**（刚访问的数据很可能再被访问，如循环变量）+ **空间局部性**（相邻地址很可能被一起访问，如数组顺序遍历）。
- **缓存行（Cache Line）**：主存与缓存之间以 **64 字节**为块传输。顺序遍历数组能"一次读一行、用满整行"，而链表/随机访问则每步都可能缓存未命中——**这正是 ECS/SoA 布局比 OOP/AoS 快的根本原因**（呼应 §10.16）。
- **MESI 协议**：多核缓存一致性的经典协议，每个缓存行处于 **M**odified / **E**xclusive / **S**hared / **I**nvalid 之一；某核要写共享行时需先让其他核的副本失效。
- **伪共享（False Sharing）**：两个线程各改**不同变量**，但它们落在**同一缓存行**里 → 缓存行在核间反复失效与同步，性能骤降。**解决**：把热点变量按缓存行填充/对齐（`alignas(64)`、C# 的 `[StructLayout]` 手动填充），或让每个线程处理独立的数据块。
- **实践结论**：多线程要"按数据划分"而不是"按字段共享"；Job System 里每个 Job 处理独立 Chunk 正是这个思路。

### 4.3.5 原子操作、CAS 与 ABA

- **原子操作**：不可被中断的读-改-写，靠 CPU 指令（x86 的 `LOCK CMPXCHG`、ARM 的 `LDREX/STREX`）实现。
- **CAS（Compare-And-Swap）**：`CAS(addr, expected, new)`——若 `*addr == expected` 则写入 `new` 并返回成功，否则失败重试。是**无锁数据结构**的基石。
- **三个经典问题**：
  1. **ABA 问题**：值从 A 改回 A，CAS 无法感知中间变化 → 用**版本号/标记**配合（`AtomicStampedReference` 思路）；
  2. **自旋开销**：高竞争下大量 CAS 失败空转 → 退避（backoff）或改用锁；
  3. **只能保护单个变量**：多字段一致性仍需锁或事务内存。
- **C# 对应**：`Interlocked.CompareExchange/Increment/Add`、`Volatile.Read/Write`、`lock`（Monitor）。**注意 Unity 的坑**：`Interlocked` 在 IL2CPP 下可用，但**不能**在 Job 里用托管同步原语；跨线程访问 Unity 对象本身就不允许（§6 的"Unity API 只在主线程碰"）。

## 4.4 编译与运行

- **四个阶段**：**预处理**（宏展开、头文件包含、条件编译）→ **编译**（词法→语法→语义→中间代码→优化→汇编）→ **汇编**（生成目标文件 .o/.obj）→ **链接**（符号解析 + 重定位，合并成可执行文件/库）。
- **词法/语法/语义分析**：词法分析把字符流切成 **token**；语法分析按文法构造**语法树**；语义分析做类型检查、符号表填充。
- **动态库 vs 静态库**：
  - 静态库（.a/.lib）：链接时**复制进**可执行文件——发布简单、无运行时依赖、体积大、更新需重新编译、多进程不共享内存。
  - 动态库（.so/.dll）：链接时只记录引用、**运行时加载共享**——节省内存（多进程共享同一份代码段）、可独立更新、部署需带库文件（"DLL 地狱"）。
- **符号修饰与 `extern "C"`**：C++ 为支持重载会对函数名做**名字修饰（name mangling）**，C 不做；跨语言调用必须用 `extern "C"` 关闭修饰，否则链接时找不到符号（见 §2.3.3）。
- **Debug / Release**：见 C++ 章节 §2.7.6（优化级别、断言、调试符号、内联与重排带来的差异）。
- **字节序**：**大端**（高位字节在低地址，网络序）vs **小端**（低位字节在低地址，x86/ARM 常见）。跨平台协议必须显式约定或用 `htonl/ntohl` 转换——项目里"包头大端、负载小端"正是这个问题的实际体现（§项目 4.1）。

## 4.5 进程间通信（IPC）

### 4.5.1 五种主要方式（★ 必考）

| 方式 | 原理 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| **管道 Pipe** | 内核缓冲区，半双工字节流；匿名管道限亲缘进程，**命名管道 FIFO** 可无亲缘 | 简单 | 只能字节流、无消息边界、容量有限、匿名管道需亲缘关系 | shell 管道、父子进程 |
| **消息队列 Message Queue** | 内核维护的消息链表，按类型收发 | 有消息边界、可按类型取、无需同步 | 有大小上限、拷贝开销 | 结构化小消息 |
| **共享内存 Shared Memory** | 多进程映射同一块物理内存 | **最快**（零拷贝） | **需自行同步**（配信号量） | 大数据量高频交换（游戏帧数据） |
| **信号量 Semaphore** | 计数器，用于互斥与同步 | 通用 | 本身不传数据 | 与共享内存配合 |
| **信号 Signal** | 内核向进程投递的异步通知（SIGKILL/SIGTERM…） | 简单、异步 | 信息量极小、不可靠 | 终止/中断通知 |
| **Socket** | 跨主机/跨进程的网络或本地（Unix Domain Socket）通信 | 可跨机器、全双工 | 开销相对大 | 服务器/跨机通信 |

**选择口径**：**要快且数据量大 → 共享内存 + 信号量**；**要结构化小消息 → 消息队列**；**要跨机器 → Socket**；**只发简单通知 → 信号**。

### 4.5.2 与"线程通信"的对比

- **线程**共享同一地址空间，通信就是**直接读写共享变量**（因此**难在同步**而非难在传输）；
- **进程**有独立地址空间，通信必须**经内核拷贝或映射**（因此**难在传输效率**）。
- 这解释了为什么游戏网络层把 socket 回调放在独立线程、只往**队列**里投递，再交给主线程处理（避免跨线程碰 Unity API）：**队列即"进程内 IPC"的轻量替代**。

## 4.6 用户态 / 内核态与 IO 模型

### 4.6.1 用户态与内核态

- **为什么划分**：把"能执行特权指令、能访问全部硬件"的代码收进内核态，用户程序跑在受限的用户态，防止应用程序破坏系统。
- **切换时机**：**系统调用**、**中断**、**异常**。切换本身有开销（保存/恢复上下文），所以"频繁小系统调用"要合并（如 `writev`、缓冲读写）。
- **系统调用**：用户态通过软中断/专用指令陷入内核，由内核代为完成（文件读写、网络收发、内存映射都是）。

### 4.6.2 五种 IO 模型（★★★ 高频）

以"读 socket 数据"为例，关键区别是**等待数据**与**拷贝数据**两个阶段由谁承担：

| 模型 | 等待数据 | 数据拷贝 | 特点 |
| --- | --- | --- | --- |
| **阻塞 IO** | 用户线程阻塞 | 阻塞 | 最简单；一连接一线程，无法支撑高并发 |
| **非阻塞 IO** | 轮询（返回 EAGAIN） | 阻塞 | 不阻塞等待但要**忙轮询**，白烧 CPU |
| **IO 多路复用** | `select/poll/epoll` 阻塞在**多个 fd** 上 | 阻塞 | **一个线程管大量连接**，高并发标准方案 |
| **信号驱动 IO** | 内核就绪后发信号 | 阻塞 | 少用，信号处理复杂 |
| **异步 IO（AIO）** | 不阻塞 | **内核完成拷贝后通知** | 真正的"全异步"；Linux `io_uring`、Windows IOCP |

- **同步 vs 异步的判定标准**：**数据拷贝阶段是否阻塞用户线程**。所以前四种（含 IO 多路复用）都算**同步 IO**——这是最容易被追问错的一点。
- **select / poll / epoll 对比**：

| | select | poll | epoll |
| --- | --- | --- | --- |
| 数据结构 | 位图 | 数组 | 红黑树 + 就绪链表 |
| fd 上限 | 有（FD_SETSIZE，通常 1024） | 无 | 无（受系统 fd 上限） |
| 复杂度 | O(n) 每次全量遍历 | O(n) | **O(1)** 只返回就绪的 |
| 触发模式 | 水平触发 | 水平触发 | **水平 + 边缘触发** |
| 拷贝开销 | 每次调用都要把 fd 集合拷入内核 | 同 | **只在注册时拷一次** |

- **水平触发（LT）vs 边缘触发（ET）**：LT 只要还有数据就**反复通知**（编程简单，漏读也没事）；ET 只在**状态变化时通知一次**（必须一次读到 `EAGAIN`，否则数据会"躺着不动"），配非阻塞 IO 使用、效率更高。
- **与项目的联系**：游戏客户端一般**不需要**自己写 epoll——战斗网络多在独立线程里做阻塞式收发 + 队列投递（§项目 4.1）；但"为什么用独立线程 + 队列"、"为什么不能每帧轮询 socket"这类追问，答案就落在本章。服务器侧（本项 .NET 8 微服务）则常用 `async/await` + 异步 IO。

## 4.7 高频速记

- 进程=资源分配单位，线程=调度单位，协程=用户态协作式；
- 进程状态三陷阱：阻塞→就绪（不是运行）、就绪不可能→阻塞、时间片完→就绪；
- 死锁四条件：互斥、占有并等待、不可剥夺、循环等待——工程上最常破坏**循环等待**（统一加锁顺序）；
- 死锁≠饥饿≠活锁；
- 页面置换：OPT 不可实现、FIFO 有 Belady 异常、LRU 最常用但有开销、Clock 是近似；
- 对齐：成员偏移按 `min(自身大小, 对齐系数)` 补齐，结构体总大小按最大对齐值补齐；
- 缓存行 64B，伪共享靠填充/按数据划分避免；
- CAS 三坑：ABA、自旋开销、只能保护单变量；
- IPC 最快的是共享内存（但要自己同步）；
- 五种 IO 模型里只有**异步 IO**才是异步，其余（含多路复用）都是**同步 IO**。
