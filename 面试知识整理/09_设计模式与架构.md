# 九、设计模式与架构

> 本章按**功能**分为三大区：**9.1 设计模式**（代码级复用范式，按创建型/结构型/行为型细分）、**9.2 框架与架构**（工程级组织方式，含 UI 架构、ECS、分层、事件驱动、数据驱动）、**9.3 AI 行为架构**（行为树与有限状态机）。

## 9.1 设计模式（Design Patterns）

### 9.1.1 分类总览

设计模式按**目的（功能）**分为三类（★ 越多 = 面试越高频）：

| 类别 | 收录模式 | 一句话作用 |
| --- | --- | --- |
| 创建型 | 单例 ★★★、工厂 ★★★、对象池 ★★、建造者 ★、原型 ★★ | 控制对象"如何被创建" |
| 结构型 | 代理 ★★、适配器 ★★★、装饰器 ★★★、组合 ★★、外观 ★★、享元 ★★、桥接 ★ | 处理对象"如何组合与适配" |
| 行为型 | 观察者 ★★★、策略 ★★★、状态 ★★★、命令 ★★★、模板方法 ★★、责任链 ★、中介者 ★、迭代器 ★ | 处理对象间"如何协作与通信" |

### 9.1.2 创建型模式：单例、工厂、对象池、建造者、原型

- **单例（Singleton）★★★**：保证一个类全局只有一个实例，提供全局访问点；注意线程安全与生命周期管理。**游戏应用**：全局管理器（音频、存档、事件中心）、GameManager。
- **工厂（Factory）★★★**：把对象创建逻辑与使用逻辑解耦（简单工厂 / 工厂方法 / 抽象工厂），便于扩展新类型。**游戏应用**：敌人/道具生成器、技能对象创建。
- **对象池（Object Pool）★★**：复用对象，避免频繁创建/销毁（子弹、特效、怪物），减少 GC 与卡顿；优缺点、适用场景与实现思路见 Unity 章节 §6.10.1。
- **建造者（Builder）★**：把复杂对象的构建过程与表示分离，支持链式分步构造。**游戏应用**：角色属性装配、复杂 UI 弹窗、可配置对象构建。
- **原型（Prototype）★★**：通过克隆已有实例创建新对象，避免重复初始化。**游戏应用**：技能/装备模板克隆、敌人复制（C# `MemberwiseClone` 浅拷贝 / 序列化深拷贝）。

### 9.1.3 结构型模式：代理、适配器、装饰器、组合、外观、享元、桥接

- **代理（Proxy）★★**：为对象提供替身/包装以控制访问（延迟加载、权限控制、日志）。**游戏应用**：资源异步加载代理、网络请求代理。
- **适配器（Adapter）★★★**：把一个类的接口转换成客户端期望的另一个接口，解决接口不兼容。**游戏应用**：接入第三方 SDK（广告/支付）统一包装、多平台输入接口适配。
- **装饰器（Decorator）★★★**：动态给对象添加职责，比继承更灵活，避免子类爆炸。**游戏应用**：Buff/装备加成叠加（攻击力 + 吸血 + 减速层层包装）。
- **组合（Composite）★★**：把对象组织成树形结构，叶子与容器一致对待。**游戏应用**：UI 树、场景节点树、技能树（Unity GameObject/Transform 天然是组合结构）。
- **外观（Facade）★★**：为复杂子系统提供统一入口，隐藏内部细节。**游戏应用**：一键启动游戏流程（加载配置→资源→场景→主界面）、SDK 统一入口。
- **享元（Flyweight）★★**：共享不变数据，减少内存占用。**游戏应用**：大量同类对象共享贴图/网格/配置（同种子弹、场景树木）。
- **桥接（Bridge）★**：把抽象与实现分离，二者可独立变化。**游戏应用**：渲染抽象与平台实现分离（游戏开发中较少直接使用）。

### 9.1.4 行为型模式：观察者、策略、状态、命令、模板方法、责任链、中介者、迭代器

- **观察者（Observer）★★★**：定义对象间一对多的依赖关系，当被观察者状态变化时，自动通知所有观察者。
  - 优点：松耦合；可扩展；符合开闭原则；实时更新；简化对象关系。
  - 缺点：性能问题（频繁通知）；内存泄漏风险（观察者未正确注销）；更新顺序不可控；调试困难；可能被过度使用。
  - 适用场景：事件驱动系统、数据同步、发布-订阅系统、游戏事件系统（UI 监听玩家状态等）。
- **策略（Strategy）★★★**：把一族算法各自封装成可替换的策略，运行时自由切换。**游戏应用**：伤害计算（普通/暴击/元素）、移动方式、AI 行为策略切换。
- **状态（State）★★★**：把对象在不同状态下的行为封装成独立状态类，切换状态即切换行为对象。**游戏应用**：角色状态机（待机/移动/攻击/受击/死亡），比一堆 if-else 更易维护（与 §9.3 FSM 对应）。
- **命令（Command）★★★**：把请求封装成对象，支持排队、撤销、重做、宏命令。**游戏应用**：输入系统（按键→命令对象）、技能施放、录像回放、撤销操作。
- **模板方法（Template Method）★★**：父类定义算法骨架，子类重写其中步骤。**游戏应用**：关卡流程（加载→战斗→结算）、通用任务/流程基类。
- **责任链（Chain of Responsibility）★**：多个处理者依次尝试处理请求，直到有人接手。**游戏应用**：事件/消息管道（输入→UI→逻辑层层传递）、异常处理链。
- **中介者（Mediator）★**：用一个中介对象协调多个对象，避免网状引用。**游戏应用**：战斗系统与 UI/音效/成就解耦（事件总线的显式版，见 §9.2.4）。
- **迭代器（Iterator）★**：顺序访问集合而不暴露内部结构。**游戏应用**：C# `foreach`/`IEnumerable` 天然实现，遍历容器、配置表。

## 9.2 框架与架构（Framework & Architecture）

**为什么游戏不只用 MVC**：游戏状态每帧都在变、玩法逻辑复杂多变，传统 MVC 容易让 Controller 膨胀、View 与 Model 依然耦合；因此游戏业界更常见的组合是——**UI 层用 MVP/MVVM、逻辑层用 ECS 或模块化分层、整体用事件驱动 + 数据驱动**。

### 9.2.1 UI 架构：MVC / MVP / MVVM

**三大 UI 框架对比**：

| 对比项 | MVC | MVP | MVVM |
| --- | --- | --- | --- |
| 结构 | Model / View / Controller | Model / View / Presenter | Model / View / ViewModel |
| 通信方式 | Controller 监听事件、控制逻辑并更新 View | Presenter 持有 View 接口，接收操作、改 Model 后经接口刷新 View | ViewModel 通过**数据绑定**自动同步 View，逻辑全在 ViewModel |
| 耦合度 | View 与 Model 仍有耦合 | View 与 Model 完全解耦 | View 与 Model 完全解耦 |
| 可测试性 | 一般 | 好（Presenter 可脱离 UI 单测） | 好（ViewModel 可单测） |
| 典型场景 | 简单页面 | Android、Unity UI | WPF、Unity 数据绑定框架（UniRx） |

**MVC（Model-View-Controller）**：

- **Model（模型/数据）**：数据与业务逻辑。
- **View（视图）**：UI 的显示。
- **Controller（控制器）**：监听所有事件、控制逻辑流转；控制器可以拿到视图做出 UI 操作改变，视图控制 UI 的改变。
- 常见做法：每个页面一个控制器；所有事件由控制器监听；视图负责 UI 表现。

**MVP（Model-View-Presenter）**：

- View 只负责显示、只暴露接口；Presenter 持有 View 接口，处理用户操作与业务逻辑，更新完 Model 后调用接口刷新 View。
- 优点：View 与 Model 完全解耦、可单元测试；缺点：View 与 Presenter 几乎一一对应，代码量偏大。
- 适用：Unity UGUI 页面框架（页面脚本只做显示，逻辑下沉到 Presenter）。

**MVVM（Model-View-ViewModel）**：

- ViewModel 是 View 的状态与行为模型，通过**数据绑定**在 View ↔ ViewModel 之间自动同步，逻辑全在 ViewModel，View 里几乎没有逻辑代码。
- 优点：UI 与逻辑彻底分离、省去手动刷新 UI 的代码；缺点：绑定机制调试困难、有反射/序列化开销、小型项目易过度设计。
- 参考：WPF（典型代表）；Unity 中可用 UniRx/UniTask 或自研绑定实现。

### 9.2.2 ECS（Entity-Component-System）与 Unity DOTS

- **Entity**：纯 ID，没有数据也没有逻辑；**Component**：纯数据（位置、血量）；**System**：纯逻辑（移动系统、伤害系统）。
- 优点：同类数据紧凑连续排列 → **缓存命中率高、可并行计算**（Job System + Burst），天然数据驱动，适合海量实体（弹幕、RTS 单位、开放世界同屏大量物体）。
- 缺点：学习曲线陡、面向数据编程（DOP）与常规 OOP 思维冲突、调试困难、工具链相对不成熟。
- Unity 对应：DOTS（Entities + Job System + Burst），全屏数万单位仍能保持流畅。
- **完整知识体系**（Entity/Component/System、Archetype/Chunk、ECB、Burst/Job、高频面试题）见 ECS 章节 §11。

### 9.2.3 分层架构（Layered Architecture）

- 常见分层：**表现层**（UI/渲染）→ **逻辑层**（玩法/业务系统）→ **数据层**（配置/存档/网络协议）。
- 规则：上层依赖下层、禁止反向依赖；层间通过接口交互。
- 优点：职责清晰、可整体替换（换 UI 不动逻辑）、易测试；缺点：层次多了传参繁琐，过度分层会拖慢迭代。
- 游戏示例：UI 层（MVC/MVP） + 玩法系统层（模块化 Manager） + 数据层（配置表 + 存档 + 网络）。

### 9.2.4 事件驱动 / 事件总线（Event Bus、消息中心）

- 模块间不直接引用，通过全局事件中心发布/订阅：如"玩家死亡"广播一次，UI、成就、音效各自订阅处理。
- 是观察者模式（§9.1.4）的工程化封装：C# `event`/委托、自研 MessageCenter、轻量事件库。
- 优点：彻底解耦、新增监听者不影响发送方；缺点：全局事件难追踪、"隐式依赖"易滥用、高频事件有性能与内存泄漏（未注销）风险。

### 9.2.5 数据驱动（配置表驱动）

- 技能、关卡、道具、怪物数值全部进配置表（Excel/Json/ScriptableObject），代码只写通用逻辑，**改表即改玩法**，策划无需等程序发版。
- 优点：调参方便、少改代码、利于热更新；缺点：表结构设计难度大，配置校验不足易出线上 bug。

### 9.2.6 其他架构补充

- **服务定位器（Service Locator）**：全局注册/获取服务（音频、存档、网络），常配合单例统一管理模块生命周期。
- **组件式/组合架构**：功能拆成可插拔组件挂载（Unity GameObject + Component 原生思路）。
- 一个成熟的 Unity 项目通常是**分层 + 事件驱动 + 数据驱动 + UI 用 MVP/MVVM + 海量实体用 ECS** 的混合架构，面试时按这套组合回答更贴近实战。

## 9.3 AI 行为架构：行为树（Behavior Tree）与有限状态机（FSM）

| 对比项 | 行为树 | 有限状态机（FSM） |
| --- | --- | --- |
| 结构 | 树形结构，组合节点（序列/选择）、装饰节点、条件节点、行为节点 | 状态 + 事件驱动转换（如行走、攻击、死亡；玩家靠近、血量不足） |
| 执行 | 自顶向下遍历，根据节点返回状态（成功/失败/运行中）动态选择执行路径 | 每个状态独立定义行为，状态转换由事件和条件触发 |
| 优点 | 模块化、分层、可复用、易于扩展和调试 | 简单直观、实现容易 |
| 缺点 | 实现复杂、性能开销略大 | 状态多时难以维护、扩展性差 |
| 适用 | 复杂 AI（NPC 决策） | 简单明确的有限状态（角色状态） |

- 两者常结合使用：**FSM 管宏观状态切换**（巡逻/追击/战斗），**行为树管状态内的精细决策**（追击中如何绕障碍、选择技能）。
