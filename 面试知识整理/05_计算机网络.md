# 五、计算机网络

## 5.1 网络基础

### 5.1.1 网络分类

- **局域网（LAN）**：某一小区域内多台设备互联的计算机组。
- **城域网（MAN）**：一个城市范围内，几十到一百公里。
- **广域网（WAN）**：连接不同地区/城市/国家的远程网络，几十到几千公里。
- **互联网（因特网）**：目前国际上最大的网络，定义了通信规则等。
- **万维网（WWW）**：基于互联网的网站和网页的统称。
- **以太网**：网络连接的一种规则，定义了连接传输规范。

### 5.1.2 常见网络拓扑

总线型、星型、环形、树型、网状、混合型。

### 5.1.3 设备如何通信 / IP 与端口

- 原理：设备通过物理连接互联，数据封装成带地址信息的数据包，经路由选择合适的路径，经过多个中间节点到达目的地；接收端解封装交给应用程序；过程含错误检测与纠正。
- **IP 地址**：唯一标识网络中的每个设备。
- **端口**：区分同一设备上的不同服务/应用程序。
- 两者结合确保数据能从源设备的一个应用准确发送到目标设备的对应应用。

### 5.1.4 OSI 七层模型

| 层 | 功能 |
| --- | --- |
| 物理层 | 物理接口标准（电压、线缆、插头），提供比特流传输 |
| 数据链路层 | 相邻节点间数据帧可靠传输，含错误检测/纠正、流量控制（LLC、MAC 子层） |
| 网络层 | 源到目的的数据包路由选择、逻辑寻址（IP、ICMP） |
| 传输层 | 端到端传输、进程到进程（TCP 可靠、UDP 不可靠；端口号在这一层） |
| 会话层 | 会话的建立、管理和终止，同步与恢复会话 |
| 表示层 | 数据格式化、加密解密、压缩 |
| 应用层 | 应用程序间通信服务（HTTP、FTP、SMTP、DNS 等） |

### 5.1.5 TCP/IP 四层模型

| 层 | 主要协议/功能 |
| --- | --- |
| 应用层 | HTTP、FTP、SMTP、DNS 等 |
| 传输层 | TCP、UDP |
| 网络层 | IP（寻址与路由）、ICMP |
| 链路层 | ARP、RARP、以太网协议等 |

### 5.1.6 游戏服务器架构

- 布局架构：**分布式**（多服务器实例 + 负载均衡）。
- 通信模型：**C/S 客户端/服务器模型**。
- 服务器通常处理：状态同步（位置、物品、血量）、逻辑处理（剧情/NPC）、网络通信、安全验证、负载均衡、数据存储、虚拟货币交易。

## 5.2 TCP 与 UDP

### 5.2.1 TCP 与 UDP 对比

| 对比项 | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接（三次握手建立） | 无连接 |
| 可靠性 | 可靠：ACK 确认、超时重传、序号排序重组 | 不可靠：无 ACK、无重传、无顺序控制 |
| 传输单位 | 字节流（无边界，需应用层分帧） | 数据报（有消息边界，一次一个完整报文） |
| 流量/拥塞控制 | 有（滑动窗口；慢启动、拥塞避免、快速重传、快速恢复） | 无 |
| 头部大小 | 20 字节 | 8 字节 |
| 通信方式 | 点对点、全双工 | 全双工；且支持广播/多播（一对多/多对多） |
| 开销 | 大（三次握手/四次挥手） | 小，延迟低 |
| 应用 | 文件传输（FTP）、网页（HTTP/HTTPS）、邮件（SMTP/IMAP/POP3） | 视频会议、在线游戏、语音（VoIP）、流媒体等实时场景 |

> **全双工（Full-duplex）**：通信双方**同时**收发数据（收发互不影响）；半双工（Half-duplex）则同一时刻只能单向传输，如对讲机；单工（Simplex）只能单向，如广播。TCP 与 UDP 的 socket 都是全双工（可同时收发）；单工/半双工/全双工描述的是**信道能力**，与协议本身无关。TCP 与 UDP 的通信方式区别只在**目标数量**：TCP 只能点对点，UDP 还能一对多/多对多。

**各自定义（一句话）**：

- **TCP（传输控制协议）**：面向连接、可靠、基于字节流的传输层协议——通过握手建连、ACK 确认与超时重传保证可靠，并提供流量/拥塞控制，适合可靠性优先的场景（文件、网页、邮件）。
- **UDP（用户数据报协议）**：无连接、不可靠、基于数据报的传输层协议——不建连、不确认不重传，头部小、延迟低，适合实时性优先的场景（音视频通话、游戏、流媒体）。

### 5.2.2 如何解决 UDP 的不可靠

UDP 自身只有 16 位校验和检错（发现错误直接丢弃、不重传），可靠传输需**应用层自行实现**：

1. **确认 + 超时重传**：接收方收到报文回 ACK，发送方超时未收到则重发。
2. **序号 + 排序去重**：为报文编号，接收方按序重组、丢弃重复包。
3. **校验/纠错**：自算校验和或纠错码，检测甚至恢复损坏数据。
4. **滑动窗口 / 停等协议**：控制发送速率，防止接收方处理不过来。
5. **现成方案**：QUIC（HTTP/3 底层，基于 UDP 的可靠传输）、KCP（游戏常用）、RUDP、WebRTC（SCTP over UDP）等。

> **游戏中的可靠 UDP**：游戏一般不用 TCP——重传与队头阻塞会造成延迟抖动，且"错过旧包不如拿新包"。可靠 UDP 常用**分级可靠（部分可靠）**：关键消息（登录、开火、拾取）走可靠重传通道；高频状态消息（位置、朝向）允许丢包，用最新状态覆盖旧值。常用方案：**KCP**（轻量可靠 UDP：ACK 确认 + 快速重传 + 滑动窗口，帧同步常用）、**ENet**（可靠/不可靠通道混合，Godot 内置）、**RUDP**（通用可靠 UDP 封装）、Unity 侧 **UDP Transport / Photon**（可靠与不可靠通道分离）、**QUIC**（可靠 + 多路复用，延迟低）。

### 5.2.3 TCP 三次握手与四次挥手

**三次握手（建立连接）**

1. 第一次：客户端发送 **SYN**（请求建立连接）；
2. 第二次：服务端回复 **SYN + ACK**（确认收到）；
3. 第三次：客户端发送 **ACK**（确认建立）。

**四次挥手（断开连接）**

1. 客户端发送 **FIN**（请求断开）；
2. 服务端回复 **ACK**（收到断开请求）；
3. 服务端发送 **FIN**（服务端准备断开）；
4. 客户端发送 **ACK**（确认断开）。

### 5.2.4 TCP 如何确保可靠传输

1. **序列号与确认机制**：序列号标识报文段第一个字节序号；接收方发送 ACK 确认，未收到则重传。
2. **重传机制**：超时重传；快速重传——接收方收到乱序报文段会发送重复 ACK，发送方收到 3 个重复 ACK 后立即重传丢失段。
3. **流量控制**：滑动窗口——接收方通过窗口大小字段告知可接收的数据量，发送方据此调整速率，避免缓冲区溢出。
4. **拥塞控制**：
   - 慢启动：窗口从很小开始、每收到一个 ACK +1 MSS（每个 RTT 约翻倍），直到达到慢启动阈值（`ssthresh`）后转入拥塞避免。
  - **初值口径**：经典 RFC 5681 是 **1 个 MSS**（面试照答即可）；**RFC 6928 已把初始窗口提高到约 10 个 MSS**（`initcwnd`，避免短连接还没爬满就结束），所以"1 个 MSS"是教科书值、现代实现多为 10。能说出这个差异是加分项。
   - 拥塞避免：达到阈值后窗口线性增长；
   - 快速恢复：发生拥塞后窗口减半，进入快速恢复，避免窗口骤降。

### 5.2.5 KCP：可靠的 UDP（游戏常用）

**是什么**：KCP 是运行在 **UDP 之上**的开源**快速可靠传输协议**（ARQ 实现，作者 skywind3000），核心思路是"用 UDP 的传输 + 自己实现 TCP 那套可靠性，但把每个环节都调快"。游戏（尤其帧同步）常用，也呼应 §5.2.2 的"可靠 UDP"。

**为什么可靠——它实现了什么（对应 TCP 的可靠机制）**：

- **确认 + 超时重传**：收包回 ACK，发送方超时未确认则重传。
- **序号 + 窗口**：每个包带序号（sn）与未确认序号（una），支持滑动窗口连续发送、按序重组、去重。
- **快速重传**：收到重复 ACK 达到阈值即重传，不等超时。阈值可配（`resend`）：**默认 0＝关闭快速重传、只靠超时重传**；开启后常用 2。
- **动态 RTO**：超时时间紧贴实测 RTT 动态计算（`rx_minrto` 下限可配到毫秒级），而非使用固定的保守下限。
- **拥塞/流控是可配置项，不是"没有"**（**本库最易答错的点**）：窗口受发送缓存与接收窗口约束；**正常模式下丢包退让与慢启动默认开启**（与 TCP 同样的公平退让），可通过 `ikcp_nodelay(kcp, nodelay, interval, resend, nc)` 逐项关掉：
  - `nodelay=0/1`：是否关闭**慢启动**与**丢包退让**（1＝关闭，即"极速模式"）；
  - `interval`：内部更新/flush 间隔（ms），越小越灵敏、越耗 CPU；
  - `resend`：快速重传阈值（0＝关闭）；
  - `nc=1`：关闭**流控**（不再受接收窗口约束）。
  - 例：`ikcp_nodelay(kcp, 1, 10, 2, 1)` 即极速模式——关慢启动+关丢包退让、10ms flush、快重传阈值 2、关流控。
  - 所以准确说法是：**KCP 默认与 TCP 一样退让，只是允许你把退让关掉换延迟**；"KCP 没有拥塞控制"只对极速模式成立。

**可靠基础上，为什么比 TCP 快**：

| 环节 | TCP | KCP |
| --- | --- | --- |
| 实现位置 | 内核协议栈（传输层） | 用户态，跑在 UDP 上（应用层） |
| 超时重传 | RTO 保守（Linux 下限 200ms；RFC 6298 建议 1s） | RTO 紧贴 RTT，`rx_minrto` 可配到毫秒级 |
| 确认时机 | 可能延迟 ACK（合并到 40ms 内） | 默认收到即回 ACK、立即 flush |
| 快速重传 | 等 3 个重复 ACK 才重传 | 阈值可配；**默认关闭**，开启后常用 2 |
| 拥塞控制 | 有且不可关：丢包视为拥塞，窗口减半/慢启动 | **默认有**（丢包退让+慢启动），但**可逐项关闭**换取速度 |
| 建连握手 | 三次握手 + 慢启动爬坡 | 无握手，UDP 即发即收；极速模式下省去慢启动爬坡 |
| 头部 | 20 字节 + 选项 | UDP 8 字节 + KCP 24 字节 |

**一句话总结"为何快"**：TCP 的保守（保守 RTO、延迟 ACK、3 次重复 ACK 才快重传、丢包即退让）大多**不可调**；KCP 把同样的机制搬到用户态并**全部开放为参数**，再通过关闭慢启动/丢包退让/流控把公平性换成速度——所以同样的丢包网络下能拿到更低延迟、更高吞吐。

**代价与适用**：

- **抢占式、不公平**：一旦关掉丢包退让与流控，与 TCP 混跑公网会挤占带宽；适合内网/自建服务器（游戏帧同步），公网大规模使用需谨慎或保留退让。
- UDP 自带问题仍需应用层处理：连接管理、NAT 穿透、MTU 分片。
- 仍是**尽力可靠**：极端弱网下延迟可能很大，此时"错过旧包拿新包"的应用层设计（状态覆盖）比逐包补发更重要。

> KCP 不是"又快又可靠还免费公平"的银弹：它把 TCP 的保守换成了激进，用**公平性换速度**，适合可控网络（游戏服务器）而不适合公共互联网。

**面试追问：KCP 比 TCP 快，为什么不全都用 KCP？**

**结论**：KCP 用公平性、稳定性和工程成本换速度，只适合带宽充足、网络可控的场景。

1. **关掉退让就不公平**：KCP 极速模式可关闭丢包退让与流控；公网链路共享且会真拥塞，别人退让它不退 → 重传风暴 → 拥塞崩溃，比 TCP 更慢。保留默认退让则与 TCP 相当。
2. **多数场景不需要**：低频小消息两者延迟差异极小；高丢包时关闭流控硬发会产生大量无效重传，有效吞吐反而低于 TCP。
3. **工程成本高**：连接管理、NAT 穿透、分片、心跳、加密都要自做；TCP 内核现成 + TLS 生态。
4. **已有标准答案**：QUIC 提供 0-RTT、多路复用免队头阻塞、标准加密。

**选型**：公网 → TCP；可控网络求低延迟 → KCP；游戏内：登录/开火 → TCP，位置/朝向 → 不可靠 UDP，帧同步 → KCP。

### 5.2.6 粘包 / 拆包与协议分帧（★★★★ 必考）

- **先纠正一个常见误解**：TCP 是**字节流**协议，"粘包/拆包"不是 TCP 的 bug——它**根本不保留消息边界**，所以"一次 `recv` 读到的内容"和"发送方一次 `send` 的内容"没有对应关系。UDP 是数据报，天然有边界，不存在粘包。
- **三种表现**：
  1. **粘包**：多次 `send` 的小数据被合并成一次 `recv`（Nagle 算法、内核缓冲区合并、接收缓冲积压都会导致）；
  2. **拆包/半包**：一次 `send` 的大数据被拆成多次 `recv`（超过 MSS 被分段，或接收缓冲区不够大）；
  3. **二者混合**：一次 `recv` 收到"上一个包的尾巴 + 下一个包的头"。
- **本质**：接收方必须**自己从字节流里切出完整消息**（术语叫**分帧 framing**）。这与"TCP 可靠"不矛盾——可靠指的是"字节不丢不乱"，不是"消息有边界"。

**四种主流分帧方案（面试要能对比）**：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **定长** | 每个消息固定 N 字节 | 实现最简单 | 浪费带宽、不灵活 |
| **长度字段（最常用）** | 头部放 2/4 字节长度，先读头→得到长度→再读 body | 高效、支持变长；可一次预分配缓冲 | 需要约定字节序；长度字段本身要被信任校验（防恶意超大长度） |
| **特殊分隔符** | 用 `\n`、`\0` 等分隔 | 可读性好（文本协议常用，如 HTTP 头、Redis 协议） | 消息内不能出现分隔符，需转义；逐字节扫描有开销 |
| **自描述/固定头 + 变长体** | 固定头（含长度与类型）+ 变长负载 | 工程上最实用，游戏协议标配 | 略复杂 |

- **工程实现要点（答题加分）**：
  1. **必须循环读到"够一个包"为止**：`recv` 返回的字节数是不确定的，正确做法是"**累积到缓冲区 → 够一个头就解析长度 → 够一个完整包就取出 → 剩余留在缓冲区等下次**"；只在"一次 recv 就是一个完整包"的假设下写代码是典型错误。
  2. **`recv` 返回 0 表示对端正常关闭**（不是"读到空数据"）；返回 −1 且 `errno` 为 `EINTR` 应重试，`EAGAIN/EWOULDBLOCK` 表示非阻塞下暂时无数据。
  3. **长度字段要校验上限**（如 > 1MB 直接断连），否则恶意长度会导致预分配爆内存。
  4. **TCP_NODELAY**：若协议本身已经分帧且消息小，通常要**关掉 Nagle** 以降低延迟（见 §5.2.8）。
- **与项目联动**：本项目 TCP 通道与 KCP 通道都在包头放了 `PkgLen`（见项目 §4.1 的 19 字节公共头），接收侧按长度字段切包——**这就是"长度字段分帧"的实例**。被追问"你们怎么解决粘包"时，答"包头带长度 + 接收缓冲累积 + 循环切包"，而不是"TCP 会自动分包"。

### 5.2.7 TCP 状态转换：TIME_WAIT / CLOSE_WAIT 与 2MSL（★★★ 高频）

**四次挥手与状态**（主动关闭方 vs 被动关闭方）：

```
主动关闭方（Client）                     被动关闭方（Server）
ESTABLISHED                             ESTABLISHED
   │ FIN, seq=u  ──────────────────────→
FIN_WAIT_1                              CLOSE_WAIT   ← 收到 FIN，等本端应用关闭
   │ ←────────────── ACK, ack=u+1
FIN_WAIT_2
   │ ←────────────── FIN, seq=w        LAST_ACK
   │ ACK, ack=w+1 ─────────────────────→
TIME_WAIT（等 2MSL）                     CLOSED
   │
CLOSED（2MSL 超时后）
```

- **为什么需要 TIME_WAIT（等 2MSL）**，两个理由：
  1. **保证最后一个 ACK 能到达对端**：若该 ACK 丢失，对端会重传 FIN；此时本端若已 CLOSED，就会回 RST 导致对端异常。留在 TIME_WAIT 才能重发 ACK。
  2. **让本次连接的旧报文在网络中自然消亡**：防止延迟的旧报文被**同一四元组的新连接**误收（序列号可能撞上）。
- **MSL**（Maximum Segment Lifetime）是"报文在网络上能存活的最长时间"，**2MSL 即"一去一回"的上界**（Linux 上 MSL 常取 30s，故 TIME_WAIT 约 60s）。
- **TIME_WAIT 过多（服务器常见问题）**：短连接高并发时会积累大量 TIME_WAIT，占端口/内存。应对：
  - **用长连接**（根本解法，游戏登录/逻辑通道正是长连接）；
  - 调 `net.ipv4.tcp_tw_reuse`（**安全**：仅对**出向**连接复用 TIME_WAIT 的端口，需开启时间戳）；
  - **不要**轻易用 `tcp_tw_recycle`（已在 Linux 4.12 移除，NAT 环境下会导致连接异常）；
  - 扩大本地端口范围、增加 `somaxconn` 等。
- **CLOSE_WAIT 过多 = 代码 bug**（这一点最容易被追问）：CLOSE_WAIT 表示"**对端已经关了，本端还没调用 `close()`**"——即**应用层忘记关闭 socket**（连接泄漏）。所以两者的定性完全不同：

| | TIME_WAIT | CLOSE_WAIT |
| --- | --- | --- |
| 谁的状态 | **主动关闭方** | **被动关闭方** |
| 含义 | 正常收尾等待期 | 本端**尚未 close**，等待应用处理 |
| 数量多说明 | 短连接太多（可调优） | **应用没关连接（bug，要改代码）** |
| 处理 | 长连接 / `tw_reuse` / 扩端口 | 检查代码泄漏：异常分支未 close、连接池未回收 |

- **相关攻击/异常**：**SYN Flood**（半连接队列 `syns queue` 被打满 → 开启 `tcp_syncookies`）；**RST 攻击**（伪造 RST 断连）。面试答到"半连接队列 / accept 队列"即可，不必深挖。

### 5.2.8 Nagle 算法与 TCP_NODELAY（★★ 游戏高频）

- **Nagle 算法**（RFC 896）：为减少小包、提升带宽利用率——**若还有未被 ACK 的小数据，就先把后续小数据攒起来，等到 ACK 到达或攒够一个 MSS 再发**。
- **它带来的问题：延迟**。在"请求-响应"式的小消息协议里（如游戏操作指令），会出现经典的 **Delayed ACK + Nagle 互相等待**：本端等 ACK 才发下一小包，对端却在延迟 ACK（Linux 最多等 40ms）——**平白引入几十毫秒延迟**。
- **解决**：设置 **`TCP_NODELAY`**（C# 中 `socket.NoDelay = true`）关闭 Nagle，让每个 `send` 立即发出。**游戏客户端几乎总是打开 `NoDelay`**。
- **什么时候反而该留着 Nagle**：批量传输大文件、对延迟不敏感且想减少小包开销时。
- **与应用层心跳的区别**：Nagle 管"何时发"；**KeepAlive** 是 TCP 层的**空闲探测**（默认 2 小时才开始，且只探测"连接是否还活着"，间隔按系统配置）——**游戏不能用 TCP KeepAlive 代替应用层心跳**，因为它太慢、不可配、且无法传递业务信息。应用层心跳（如项目 §4.5 的 1s/0.5s 双通道）才能做到"秒级发现掉线 + 顺带测延迟 + 保 NAT 映射"。

## 5.3 HTTP 与 DNS

### 5.3.1 HTTP 基础与请求响应

- **HTTP 连接建立流程**：DNS 解析 → TCP 三次握手（HTTPS 还要 TLS 握手）→ 发送 HTTP 请求 → 接收响应。
- **协议定位**：HTTP 是**应用层**的"请求-响应"式、**无状态**协议（服务器默认不记上一次请求）；无状态带来的问题靠 **Cookie / Session / Token** 弥补。
- **请求方法**：

| 方法 | 语义 | 幂等 | 安全 |
| --- | --- | --- | --- |
| GET | 获取资源 | 是 | 是 |
| POST | 提交/创建（非幂等） | 否 | 否 |
| PUT | 全量替换（幂等） | 是 | 否 |
| PATCH | 局部更新 | 否 | 否 |
| DELETE | 删除 | 是 | 否 |
| HEAD / OPTIONS | 只取头 / 预检（CORS 用） | 是 | 是 |

- **GET 与 POST 的区别**（老题但常问，要点是"语义"而非"能不能传 body"）：

| | GET | POST |
| --- | --- | --- |
| 语义 | 获取（只读、可缓存、可收藏、可回退） | 提交（会改状态） |
| 参数位置 | 通常在 URL query | 通常在 body |
| 长度限制 | 受 URL 长度限制（浏览器/服务器各自限制） | 基本无限制 |
| 幂等/缓存 | 幂等、可被缓存 | 非幂等、默认不缓存 |
| 安全性 | 参数明文在 URL（会进日志/历史） | 相对隐蔽，但**都不加密**——安全性靠 HTTPS，不靠选方法 |

- **常见状态码（按类记）**：
  - **2xx 成功**：200 OK、201 Created、204 No Content；
  - **3xx 重定向**：**301 永久**（会被浏览器缓存，慎用）、**302/307 临时**（302 可能改方法，307/308 保持方法）、**304 Not Modified**（配合 `If-Modified-Since`/`ETag` 做协商缓存——**热更/CDN 的核心机制**）；
  - **4xx 客户端错**：**400** 参数错、**401** 未认证、**403** 无权限、**404** 不存在、**429** 限流；
  - **5xx 服务端错**：**500** 内部错误、**502** 网关收到坏响应、**503** 不可用、**504** 网关超时。
- **HTTP/1.1 → 2 → 3 的演进（面试加分）**：

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- |
| 传输层 | TCP | TCP | **QUIC（基于 UDP）** |
| 并发 | 每域名 6 条连接 + 队头阻塞 | **多路复用**（一个连接并发多流），但**TCP 层仍有队头阻塞** | 多路复用 + **彻底消除队头阻塞** |
| 头部 | 文本、重复传输 | **HPACK 头部压缩** | QPACK |
| 握手 | TCP + TLS 各一次 | 同 | **0-RTT/1-RTT**，建连更快 |
| 适用 | 兼容性最好 | 主流 | 弱网/移动端优势明显 |

- **与项目联动**：热更走 HTTP/CDN 下载资源包，**用 304 + ETag/Hash 做"是否需要下载"的判断**——这正是项目"Hash 差异下载"的底层依据（项目 §5.2）。

### 5.3.2 DNS 解析过程（★★ 常考）

**递归 + 迭代两步走**：

1. **本机**：先查**浏览器缓存 → 系统 hosts → 本地 DNS 缓存**；未命中则向**本地 DNS 服务器**（运营商/公共 DNS）发起**递归查询**。
2. **本地 DNS 服务器**替客户端做**迭代查询**：
   - 问**根域名服务器** → 返回顶级域（`.com`）服务器地址；
   - 问**顶级域服务器** → 返回权威域名服务器地址；
   - 问**权威域名服务器** → 拿到最终 IP，回给客户端并**按 TTL 缓存**。

- **记录类型**：`A`（IPv4）、`AAAA`（IPv6）、`CNAME`（别名，CDN 常用）、`MX`（邮件）、`NS`（权威服务器）、`TXT`（校验）。
- **为什么游戏/热更需要 DNS**：CDN 靠 **CNAME + 智能解析**把用户导向最近的边缘节点；**故障转移**与**负载均衡**也靠 DNS 权重/健康检查实现。
- **DNS 的坑**：**DNS 劫持/污染**（明文 UDP 53）→ 用 **DoH/DoT** 加密；**TTL 缓存**导致切换 IP 后仍有用户打到旧节点（所以 CDN 切换要"先降 TTL 再切"）。
- **优化**：**HTTPDNS**（用 HTTP 直接拿 IP，绕过本地 DNS，抗劫持、可精准调度）——国内手游常用。

### 5.3.3 HTTPS 与 TLS 握手（★★★ 必考）

- **HTTPS = HTTP + TLS**，解决 HTTP 明文的三大问题：**窃听**（加密）、**篡改**（完整性校验）、**冒充**（身份认证）。
- **混合加密**：**非对称加密**（RSA/ECDHE）只用于**握手阶段协商出会话密钥**，之后用**对称加密**（AES 等）传数据——因为对称加密快得多。
- **证书链与验证**：服务器出示证书 → 客户端用**内置 CA 根证书**逐级验证签名 → 校验证书**域名匹配、有效期、是否被吊销（CRL/OCSP）**。**自签名证书会报警**，就是因为没有可信 CA 背书。
- **TLS 1.2 握手（RSA 密钥交换，简化）**：
  1. Client Hello（支持的版本/套件、**随机数 A**）；
  2. Server Hello（选定套件、**随机数 B**）+ 证书；
  3. 客户端验证证书 → 用证书公钥加密**预主密钥**发过去；
  4. 双方用 A + B + 预主密钥派生**会话密钥**；
  5. 交换 Finished 校验 → 开始对称加密通信。
- **TLS 1.3 的改进**：握手从 **2-RTT 降到 1-RTT**（甚至会话恢复 **0-RTT**）；**废除了 RSA 密钥交换**，强制**前向安全**的 (EC)DHE——即使服务器私钥日后泄露，也无法解密历史流量。
- **前向安全（Forward Secrecy）**：每次会话的密钥独立，长期私钥泄露不影响过去的会话。这是"为什么 TLS 1.3 禁用 RSA 密钥交换"的答案。
- **游戏里的现实**：**战斗高频通道一般不做 TLS**（握手与加密开销、且 KCP 已经跑在 UDP 上）；**登录/支付/HTTP 接口走 TLS**。所以项目里"TCP 登录通道 + UDP 战斗通道"的分工，部分原因就在这里。

### 5.3.4 序列化方案与协议设计（项目相关的追问）

- **为什么网络协议要序列化**：把内存对象变成**确定字节序列**，两端才能解出一致结果；要关心**体积、CPU 开销、跨语言、版本兼容**。
- **常见方案对比**：

| 方案 | 体积 | 速度 | 跨语言 | 特点 |
| --- | --- | --- | --- | --- |
| JSON | 大 | 中 | 好 | 可读、易调试；解析慢、GC 高 |
| Protobuf | 小 | 快 | 好 | 需 .proto 与代码生成；字段号保证兼容 |
| **MemoryPack** | **很小** | **很快** | C# 优先 | **源码生成、零反射、支持多态/循环引用**；本项目采用 |
| MessagePack | 小 | 快 | 好 | 二进制版 JSON，动态结构 |

- **协议设计要点**：
  1. **包头固定 + 变长体**（长度字段分帧，见 §5.2.6）；
  2. **协议号（cmd）路由**到处理函数（项目用"注册表：cmd → 处理函数"）；
  3. **请求-响应关联**：`MsgId` + 超时回调（项目 §4.3.2），避免"全局串行等回包"；
  4. **版本兼容**：预留字段、字段号不复用、新增字段给默认值；
  5. **字节序显式约定**（项目：包**头大端**、**负载按 MemoryPack 默认小端**——必须写进协议文档，见项目 §4.1）。

- **协议层次（一句话）**：DNS/HTTP 在应用层，TCP/UDP 在传输层，IP 在网络层；**网络协议的作用**是定义数据在网络中传输的规则与标准，确保不同系统之间能正确交换信息。

### 5.3.5 DNS 与 HTTP 速记

- 粘包不是 TCP 的错，是"字节流无边界"；解决靠**长度字段 + 缓冲累积 + 循环切包**；
- **TIME_WAIT 多 = 短连接多（可调优）；CLOSE_WAIT 多 = 代码忘了 close（要改代码）**；
- 2MSL 的两个理由：**保证最后 ACK 送达 + 让旧报文消亡**；
- Nagle + Delayed ACK 会互等几十毫秒，**游戏开 `TCP_NODELAY`**；
- TCP KeepAlive 默认 2 小时，**不能替代应用层心跳**；
- HTTP 无状态 → Cookie/Session/Token；**304 是热更"要不要下载"的关键**；
- HTTP/2 多路复用但仍有 TCP 队头阻塞，**HTTP/3 用 QUIC 才彻底解决**；
- HTTPS = 非对称握手 + 对称传输；**TLS 1.3 强制前向安全、1-RTT/0-RTT**。

## 5.4 Socket 与游戏网络

### 5.4.1 什么是 Socket

- Socket 是网络编程的抽象接口，封装了 TCP/UDP 通信细节；客户端通过 Socket 建立连接、发送/接收数据；服务端通过监听 Socket 接受连接。

### 5.4.2 长连接与短连接

- **短连接**：每次通信都建立/断开连接（三次握手 + 四次挥手），适合低频请求（如 HTTP）。
- **长连接**：连接建立后保持复用，适合高频交互（游戏、即时通信）；需要心跳保活、断线检测。

### 5.4.3 心跳包与断线重连

- **心跳包**：客户端/服务器定时发送的小数据包，用于确认对方在线、检测断线、保持 NAT/防火墙映射（防止连接被回收）。
- **断线重连**：
  - 检测断线：超时检测、心跳包等；
  - 重连策略：指数退避、随机退避等；
  - 状态恢复：重连成功后恢复之前的连接状态；
  - 错误处理：处理重连过程中的各种异常。

### 5.4.4 5000 个客户端连接的处理方案

- 不能为每个连接开一个线程（线程开销太大）。
- 方案：**单线程 + 事件循环 / IO 多路复用**（select/poll/epoll/IOCP），配合**线程池**处理业务逻辑；游戏服务器常用 **Actor/异步消息模型**，客户端连接由事件驱动而非线程驱动。

### 5.4.5 客户端与服务器交互方式

- 请求-响应（同步/异步回调）、推送（服务器主动下发）、长连接实时同步、RPC（远程过程调用）。

### 5.4.6 浮点数最小传输量问题

- 题目：属性 a 为浮点数，最大 10000，保留 4 位小数（如 4.0643），如何用最少数据量传输？
- 思路：**定点化**——把小数放大 10⁴ 倍转成整数传输：`4.0643 * 10000 = 40643`，用 **4 字节 int32** 传输；接收端除以 10000 还原。比直接传字符串/浮点字符串更省带宽。

### 5.4.7 Unity 连接数据库

- 客户端一般不直接连数据库（安全性差）；常见做法：客户端通过 HTTP/WebSocket 请求服务器，由服务器访问数据库（MySQL/SQL Server 等），或使用 UnityWebRequest 调用后端 API；编辑器内可用 ODBC/第三方插件直连调试。

## 5.5 游戏同步：状态同步 vs 帧同步

| 对比项 | 状态同步 | 帧同步 |
| --- | --- | --- |
| 同步内容 | 服务器定期下发游戏**完整状态**（位置、血量等） | 服务器只同步玩家**输入指令** |
| 计算位置 | 服务器计算所有游戏逻辑 | 各客户端按相同初始状态 + 输入**独立计算** |
| 带宽 | 大（状态复杂时消耗大） | 小（只传输入） |
| 响应速度 | 延迟较高 | 快、流畅 |
| 安全性 | 高，逻辑在服务器，难作弊 | 低，客户端可作弊 |
| 实现复杂度 | 简单，逻辑集中 | 复杂，需保证各端逻辑一致（确定性） |
| 适用场景 | MMORPG、回合制等实时性要求不高的游戏 | MOBA、RTS 等实时性要求高的游戏 |

**各自定义（一句话）**：

- **状态同步**：服务器运行全部游戏逻辑，定期把**完整游戏状态**（位置、血量等）下发给客户端，客户端只负责渲染表现——逻辑以服务器为准，安全但带宽大、响应慢。
- **帧同步（Lockstep）**：服务器只转发各玩家**输入指令**，各客户端用**相同初始状态 + 相同输入**独立运行同一份逻辑得出相同结果——只传输入、带宽小、响应快，但需保证逻辑确定性，且客户端可篡改输入作弊。

**选型：什么时候用状态同步 / 帧同步？**

| 决策因素 | 倾向状态同步 | 倾向帧同步 |
| --- | --- | --- |
| 同屏实体数 | 少（玩家 + 少量单位） | 海量（RTS 成百上千单位、MOBA 团战） |
| 实时/响应要求 | 低（回合制、卡牌、策略） | 高（格斗、MOBA、弹幕、音游） |
| 防作弊要求 | 高（竞技、排行、数值敏感） | 低（信任环境、内网） |
| 网络环境 | 弱网、跨区、延迟抖动大 | 网络可控、低延迟（同机房） |
| 逻辑是否可确定 | 难以确定（重物理/AI、表现随机） | 必须完全确定（固定步长、统一随机种子） |
| 服务器成本 | 带宽 + 算力开销大 | 只转发输入，成本低 |

**业界典型**：

- **状态同步**：MMORPG（魔兽世界/FF14）、FPS/吃鸡（CS、守望先锋、PUBG——服务器权威 + 客户端预测/插值补偿）、回合制卡牌。
- **帧同步**：RTS（星际争霸/帝国时代）、格斗游戏、音游、早期 MOBA——共同点是同屏单位多、操作密集、带宽敏感。
- 注意：MOBA 如 LOL 实为**状态同步**（服务器权威），"同屏人多"不等于帧同步。

**一句话总结**：**"人少、逻辑重、要防作弊、网络差" → 状态同步；"同屏单位海量、操作快、带宽紧、网络可控" → 帧同步。**

**混合方案（加分）**：实际项目常混合——核心战斗/单位用帧同步省带宽，关键结算（伤害、掉落）服务器权威复核；FPS 用状态同步 + 客户端预测/延迟补偿掩盖延迟。判断口诀：**能容忍服务器权威就用状态同步，只有同步量成为瓶颈且逻辑可确定时才上帧同步。**

**帧同步如何反作弊**：

- **输入签名/加密**：客户端输入用密钥签名（HMAC）或加密传输，防止篡改（改移动、改伤害）。
- **随机种子服务器下发**：随机数和初始状态由服务器统一分发，客户端无法控制随机结果。
- **逐帧状态哈希比对**：每帧结束各客户端上报状态哈希，服务器比对，不一致即判定作弊（改逻辑/外挂）。
- **服务器并行模拟抽验**：服务器对关键帧或随机抽帧重跑同样逻辑，与客户端结果对账（成本高，常抽样）。
- **关键操作服务端权威**：伤害、掉落、金币等敏感数据由服务器复核，客户端结果仅作参考。

## 5.6 加密与安全

- 按加解密密钥是否相同分为两大类：
- **对称加密**：同一密钥加密解密。常见：AES（高级加密标准，广泛使用）、DES（早期标准，已不推荐）、3DES（DES 的改进）。
- **非对称加密**：一对密钥（公钥 + 私钥）。公钥加密、私钥解密。常见：RSA（加密 + 数字签名）、DSA（主要用于数字签名）。
- **公钥与私钥**：公钥公开用于加密/验签；私钥保密用于解密/签名；公钥加密的数据只有对应私钥能解。
