# 七、新手引导系统

> 本章讲项目新手引导：配置表驱动 + `GUIDE_UPDATED` 事件循环的"分布式状态机"、UI 零改动的自动绑定、强/弱引导的交互接管、组粒度存档。引导系统是"配置驱动 + 事件驱动"双结合的经典实例，面试讲它最能体现工程抽象能力。

## 7.1 架构总览：配置驱动 + 事件循环（★★★）

### 7.1.1 四层结构

```
配置层  TbGuide（步骤表）/ TbGuideGroup（组表：承上组/承下组/开闭条件）
逻辑层  GuideManager（条件判定/步骤推进/存档上报）
表现层  GuideLayer(29层) → GuidePowerLayer（强引导）/ GuideDefaultLayer（弱引导）
监听层  GuideListenerObject（挂在 UI 物体上）/ GuideBattleListener（战斗 UI）
```

### 7.1.2 驱动模型：不是集中式状态机，而是"各自判定"的事件循环（★ 亮点）

```
UI 打开 / 弹窗关闭 / 断线重连 / 步骤推进 → 广播 GUIDE_UPDATED
→ 所有已挂载的监听者各自调用 ProcessGuide(自己的 guideId)
→ CheckGuideEnable（组未完成？轮到步骤？承上承下组？开闭条件？）+ CheckGuideStep（是否轮到我的步骤）
→ 是才弹出引导；玩家完成 → 步数+1 → 再广播 GUIDE_UPDATED → 下一轮判定循环
```

- **面试话术**："引导系统没有集中式状态机，而是'事件循环 + 各自判定'：每个 UI 物体上挂的监听器收到 GUIDE_UPDATED 后自己判断'是不是轮到我的引导步骤'。好处是加引导零代码改动（配置表指定层名+节点路径+步骤号即可），步骤间天然松耦合，弹窗关闭/重连等任何 UI 状态变化都能自动驱动下一步。"

## 7.2 UI 绑定机制（加引导零 UI 改动 ★★）

### 7.2.1 自动挂载：LayerContent.OnCreate 统一入口

```
任意层创建 → 按层资源名查引导配置（GetGuidesByLayerName）
→ FindDeepChild(配置的节点路径) 找监听物体
→ 自动 AddComponent<GuideListenerObject> + InitGuide(guideId)
→ 物体激活即尝试弹出
```

### 7.2.2 目标定位三通道（解决"目标还不存在"的问题）

| 通道 | 适用 | 机制 |
| --- | --- | --- |
| 普通物体 | 静态节点 | 直接 FindDeepChild 预取 |
| 动态子节点（TransformContent+Index） | 运行期生成的子物体 | 注册 `GUIDE_TRANSFORM` 事件，父节点挂数据组件，生成时广播匹配 |
| 列表项（ViewController+Index/Id/Quality） | 虚拟列表里的条目 | 注册 `GUIDE_VIEW_INDEX/ID`，列表控制器生成条目时广播，监听器校验 guideId/index/品质后弹出 |

### 7.2.3 引导期间的 UI 压制

- Dialog 层且有弹窗（NoPopLayer==false）时不弹引导；弹窗关闭触发 `GUIDE_UPDATED` 刷新——**引导与弹窗互斥由事件联动保证**；弹出前延迟遮罩防误触。

## 7.3 引导流程控制（推进/关闭/接管 ★★）

### 7.3.1 条件检查链（CheckGuideEnable 按序校验）

总开关（编辑器菜单/ENABLE_POLICY）→ 非预览场景 → 战斗引导限指定引导关卡（GUIDE_PLAY_ID）→ 步骤/组配置存在 → DungeonId 匹配当前房间 → **组未完成** → **轮到当前步骤**（GuideStepData[组]=已完成步数=下一步下标）→ 承上组已完成 / 承下组未完成 → 开启条件通过 / 关闭条件不通过。

### 7.3.2 强引导（Power）交互接管

- **Instantiate 复制目标物体**做"可点击替身"（原目标保留，替身接管点击）→ 点击 = 推进引导 + 触发真实按钮逻辑（`_targetButton.OnClick.Invoke()`）→ `_mask` 盖住防连点；
- 手指呼吸动画参数（FingerSize/FingerFrequency）来自全局配置表；
- 战斗内引导：`BattleFieldSpeed=0` 暂停战斗、隐藏右手技能组、点击引导目标时**模拟按键**（U 普攻/Space 跳/J 技能）。

### 7.3.3 弱引导（Default）与 ClickNext

- 弱引导：监听任意点击推进，非最后一步先记步数；支持拖动引导（手指 DOMove 循环到目标）；
- ClickNext：复用强引导层，目标可空，点"下一步"按钮推进；
- `ManiClose`（手动关闭）：点击引导后**不立即推进**，把推进动作存进 `LocalCloseAction`，等业务真正完成操作（如换武魂成功回调）才推进——解决"玩家没按引导做也能过"的问题。

## 7.4 存档与断点续接

- **存档粒度是"组"不是"步骤"**：服务器只记 `groupId → 是否完成`（`GuideProgressData`，组最后一步完成时发协议，RSP 成功才写）；步骤进度纯内存——**重启后未完成组从第一步重新开始**（取舍：实现简单，代价是断线重连后可能重复引导；重连恢复靠 `ResendImportantMessage` 广播 GUIDE_UPDATED 让监听器重新自检）。
- 引导组设计：`UpCarry` 承上组（必须已完成）/`DownCarry` 承下组（必须未完成）/`OpenRole` 开启条件/`CloseRole` 关闭条件——组间顺序与条件全配置化。

## 7.5 与主流程的联动（面试加分点）

- **登录后引导组 3 未完成 → 不进主城，直接进引导章节**（`GUIDE_PLAY_ID=10000`），结算不弹结算 UI，播视频后确认回大厅——新手的"第一场战斗"被整体编排；
- 新手未完成技能引导组时，进房技能未配齐**跳过提示直接进战斗**（不让新手卡在配置界面）；
- 英雄详情页在特定引导组未完成时**强制跳转技能升级页**（用 UI 路由引导玩家操作）。

## 7.6 面试话术与追问

<details>
<summary>Q：引导系统为什么不用状态机？</summary>

"步骤间有大量'等待 UI 就绪'的异步性（界面要打开、列表要生成、弹窗要关闭），集中式状态机需要每个步骤前插一堆等待逻辑，耦合爆炸。事件循环让每个监听器独立等待自己依赖的条件（界面打开/列表项生成/弹窗关闭都广播事件），谁满足谁弹——引导的编排问题变成了配置表+事件的问题。"</details>

<details>
<summary>Q：这套引导系统有什么坑？</summary>

"① 步骤进度纯内存，重启/断线后未完成组从头开始——可以接受但要如实说；② 监听器散布在 UI 树里，调试要开编辑器开关（GameTools/新手引导）；③ 老代码残留多（旧 GuideListenerComponent 整文件注释），改造时容易被误导——这是真实项目的常态，讲出来反而显诚实。"</details>
