# 六、配置与数据系统

> 本章讲两件事：**配置系统**（Luban 三层架构、外键、加载流程、热重载）与**玩家数据系统**（服务器权威 + 增量推送 + 零本地存档）。配置表驱动是面试"数据驱动"问题的最佳实例，数据权威是"防作弊"问题的最佳实例。

## 6.1 配置系统：Luban 三层架构（★★★ 必讲）

### 6.1.1 三层结构（生成 / 扩展 / 接口）

| 层 | 内容 | 职责 |
| --- | --- | --- |
| ① Luban 生成代码（`Cfg/Gen/`，239 张表，不可手改） | `Tables` 聚合类 + `TbXxx` 表类 + 行 Bean | 纯反序列化：二进制 ByteBuf → `DataMap`（主键索引） |
| ② 手写 partial 扩展 + 加工器（`CfgData/`，约 60 个 `ICustomCfg`） | Bean 的 partial 追加语义字段；`CfgInit/CfgCheck` 加工校验 | 语义加工：ID 列表预绑定成对象引用、掉落区间汇总、全局参数解析 |
| ③ 语义化访问接口（`GameCfgMgr` 静态类） | `GetXxxCfg(key, out cfg)` 统一返回 `SvrRet.Success/CantGetGameCfg` | 业务唯一入口 |

- **核心设计**：生成代码与手写代码靠 C# `partial class` 粘合——**生成器可随时重新生成，手写扩展不受影响**；加工器有注册顺序约束（如"掉落范围依赖怪物配置先完成"）。
- 面试话术："配置系统用 Luban 导出二进制表，我把它的使用模式抽象成三层：生成代码只做反序列化、手写 partial 做语义扩展与校验、业务只通过语义化接口访问——兼顾了生成效率、扩展性与类型安全。"

### 6.1.2 加载流程与数据源

- 启动 `GameCfgMgr.Initalize`：YAML 杂表 → 技能编辑器 JSON → **全表二进制一次性读入**（`new Tables(loader)`）→ 注册加工器逐个 `CfgInit` → 逐个 `CfgCheck`（错误汇总）→ 附加处理（全局参数灌入 `BattlePredefine`、子弹↔受击绑定、AI 树、敏感词）。
- 数据源：编辑器 `ResourceInfo/Config/Res/BinaryCfg/*.bytes`（238 个）；运行时 `persistentDataPath/gameres/config/*.bytes`（首启动从 StreamingAssets 拷贝、热更覆盖，§5.4）。

### 6.1.3 外键引用（Luban `_Ref` ★★）

- 反序列化只读原始 ID（`int MapID`），`ResolveRef` 阶段全表联动把 ID 换成对象引用（`MapID_Ref = TbSceneConfig.GetOrDefault(MapID)`）——**使用方直接拿对象，不用每次查表**，且天然校验了引用完整性（查不到就是 null，加工器 CfgCheck 兜底报错）。

### 6.1.4 特殊表设计

| 表 | 主键 | 用途 |
| --- | --- | --- |
| TbGlobalConfig 全局参数 | **string**（Alias） | "HitFlyGetUpTime" 等参数，Type 区分 int/string/float，加工器解析成强类型字段 |
| TbLanguage 多语言 | **string**（文案 key） | key → Desc，UI"先查表、查不到原样显示"双模式 |
| TbErrorCode 错误码 | int | 协议错误码 → 提示文案 |
| TbSystemtips 系统提示 | int | 确认框 ID → 标题/正文（支持 string.Format 占位符）/按钮文字 |

### 6.1.5 双轨与遗留（如实说）

- 技能配置**双轨**：Luban 表（供加工器）+ 技能编辑器导出 JSON（供运行时）——编辑器改完导 JSON 即生效；
- 旧版 `CsvCfgLoader`/手写表类残留（不在主加载流程，已被同名 Luban 表取代）——面试可借此讲"配置体系迁移：CSV → Luban 二进制"的演进。

## 6.2 玩家数据：服务器权威 + 纯内存缓存（★★★ 防作弊必讲）

### 6.2.1 核心结论

**玩家核心数据（英雄/背包/编队/引导/设置）没有任何本地持久化存档**——sqlite 方案已整体废弃。客户端只做内存缓存：

```
登录 → 服务器全量推送 NTF_GAME_ROLE_DATA_LOGIN（27 个字段快照）
运行期 → 每类数据独立增量推送（含删除列表）
UI 刷新 → GameEventCenter 事件广播（GAME_ROLE_DATA_UPDATED(FuncType) 等）
```

- `GameRoleDataManager`（Singleton）是唯一数据宿主，对外提供按模块分区的语义接口（GetHeroData / GetUsingTeamFormationInfo / CheckCost / GetChapterLevelIsPass / GetSystemIsUnlock）。
- 玩法面板数据（章节/商店/个人/资源）走 RSP 懒加载，同样只存内存。

### 6.2.2 增量推送协议模式（面试点）

| 数据 | NTF | 增量方式 |
| --- | --- | --- |
| 英雄 | GAME_ROLE_HERO_LIST_NTF | 逐条 merge + `DelHero` 删除列表 |
| 背包 | GAME_ITEM_ITEM_BAG_NTF | `NtfType`：1=全量替换 / 2=增量合并 |
| 编队 | GAME_BATTLE_FORMATION_INFO_NTF | `NtfType`：0=全部 / 1=增量 |
| 功能解锁 | GAME_FUNCTION_STATE_INFO_NTF | 同上 + 新解锁触发解锁弹窗 |

- 客户端写操作全部 REQ→RSP（编队保存/设置/引导完成…），RSP 成功才改本地缓存——**写操作也服务器确认**。

### 6.2.3 本地磁盘只存什么

- PlayerPrefs：设置缓存（`PlayerfrefabSettingData` JSON）、登录名/上次选服、隐私协议、每日公告日期、设备唯一码（`App_Device_Unique_ID` 防重复登录）、按 Uin 的玩法标记（钓鱼/红点/拍卖筛选）。
- persistentDataPath：热更资源与配置（§5）。
- 大版本更新（fixAppVersion 变化）→ `ClearPersistentDataPath()` 清数据。

### 6.2.4 设置系统（多端同步实例）

- 结构：`ControlSettingsData`（音量/画质/帧率/相机焦距/HDR/连招开关/摇杆模式…）；
- 读取优先级：**服务器设置 → PlayerPrefs 缓存 → 默认 json**；
- 保存：上传服务器 + 本地缓存**双写**；应用：`ApplyGameSettings` 统一下发（连招开关给 InputManager、焦距给相机、发 UPDATE_SETTINGS 事件）。

## 6.3 统计埋点（一句话带过）

- 自建埋点：`ThirdPlatLogHelper.Log<T>` → JSON → `NTF_GAME_CLIENT_LOG_REPORT` 上报游戏服务器（引导/英雄/背包/任务/战斗结果 20+ 类事件）；第三方统计 SDK（ThinkingAnalytics/Appsflyer）已移除。

## 6.4 面试话术

<details>
<summary>Q：为什么玩家数据不做本地存档？</summary>

"存档放服务器有四个好处：防作弊（改本地文件/内存无法改数值）、多设备一致（换机/重装登录即恢复）、客户端无数据一致性负担（断线重连/进程被杀不丢数据）、热更新安全（大版本清本地目录无损失）。代价是每次操作要等服务器回包——所以用'乐观更新 + 回滚'（UI 先展示、失败回退）和战斗内独立数据层（战斗镜像数据只在战斗世界内存）来抵消延迟感。"</details>

<details>
<summary>Q：配置表驱动的边界怎么把握？</summary>

"'改数值改表、改逻辑改码'。能表驱动的一律表驱动（技能时间轴/引导步骤/提示文案/掉落/全局参数）；涉及流程控制（if/else 分支）、复杂校验的留在代码（或加工器）。同时配了校验管线（CfgCheck 错误汇总 + 引用完整性）防止配错上线——数据驱动最大的坑就是配置校验不足。"</details>
